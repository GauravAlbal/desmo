## Verdict (short)

All four apps persist open/stock/reserve/start/cancel/purchase through `@ikaros/runtime` `Kernel` / `aggregate.command`. Purchase ids are saved in the runtime **before** POST. Lost HTTP replies stay `attempt_saved` + `service_unavailable`; later `order-part` / `reconcile` adopt by GET using the saved id.

They do **not** treat the runtime as the only lifecycle/amount authority:

- Shelf quantities live in host-computed `shelf_json`. The machine stores the blob; `already_stocked` / `insufficient_stock` / restock arithmetic are host branches.
- **Both change replicas** persist `mark-used` for pre-change (v1) started jobs in a JSON sidecar (`desk.usage.json` / `shop.used.json`). That file is an additional authority for `used_qty` / `used_marked`.
- **r2/change** `complete` on a v1 started job after `mark-used` returns `corrupt_state` (wrong `transaction()` step shape). New v2 jobs complete. CHANGE.md old-instance C3 is broken.
- **r2** second `reserve` is `bad_status`, not `already_reserved` (R7). r2 tests never assert that code.
- No replica calls `Machine.lookupOperation`. Purchase recovery is provider GET, which matches BRIEF R8–R12; kernel record recovery does not.

CHANGE.md requires new `mark-used` / leftover-restock `complete` on **existing started** v1 instances, while Ikaros forbids changing the frozen v1 spec and forbids a sidecar as second authority. Both builders picked the sidecar. That is a candidate/guide clash **and** an application defect.

## 1. Named writer paths

### r1/build — runtime facts, host-computed shelf

Named CLI writers (`stock-set`, `open`, `reserve`, `start`, `complete`, `cancel`, `order-part`, `reconcile`) go through `apply` → `agg.command` (`src/desk.mjs:216-219`, command sites `374-589`). Store is only `desk.sqlite`. `status` / `callback` do not write. Empty `status` does not create a store (reproduced: only `unrelated.txt` remained).

`save_purchase` is the kernel effect planner (`desk.ik.toml:69-75`; host `529-537`): `effect_id` = application purchase id, then POST. `receive_stock` commits shelf + `payment=2`.

Host `if (f.status !== ...)` branches decide the BRIEF error code before the command. The machine `from`/`when` guards are redundant with those branches. Amounts (on-hand, restock) are computed in the host and passed as `shelf_json`.

### r1/change — v2 commands plus usage sidecar for v1

Owner routing: `loadMachines` + `routeMachine` uses `machines.v1.identity.equals(agg.owner)` (`233-238`). New aggregates `create` on v2 (`277-279`). Reproduced: a store written by r1/build `./run` is shown as `started` by the change program; `complete` is `usage_unmarked` until `mark-used`.

`mark-used` on v2 calls `mark_used` (`529`). On v1 it **only** writes `STATE_DIR/desk.usage.json` (`205-206`, `526-527`) and never commits usage to the runtime. `applyUsageView` (`137-146`) prefers that sidecar over facts.

### r2/build — runtime facts, wrong second-reserve code

Same Kernel/`command` pattern (`src/desk.mjs` `stock_set`/`open`/`reserve`/`start`/`complete`/`cancel_*`/`save_purchase`/`receive_stock`). Store `shop.ik.sqlite`. Empty `status` does not create a store (reproduced).

Second `reserve`: host checks `namedState() !== "opened"` first (`387-389`), so a reserved job is `bad_status`. The later `if (f.sku) fail("already_reserved")` (`391`) is unreachable on the honest path.

### r2/change — overlay + broken v1 complete transaction

Owner routing: `ownerMachine` / `loadShop` (`223-256`) show through v2, then reopen on the owner definition. New creates use v2 (`258-261`).

`mark-used` on v2 calls `mark_used` (`523-524`). On v1 it writes `shop.used.json` (`15`, `109-126`, `525-526`). `markView` (`134-148`) reads that overlay for `started` jobs.

v1 `complete` tries `agg.transaction([{name, args}, ...])` (`557-560`). The TypeScript client maps `steps` to kernel `commands`; the kernel rejects top-level `args` (`IK_PROTOCOL_INVALID: unknown field args, expected command or observation`). Host catch maps that to `corrupt_state` (`693-696`).

## 2. Duplicate authorities / shadow state

### F1. r1/change: `desk.usage.json` is authority for usage amounts (high, application)

**Where:** `src/desk.mjs:189-206`, `137-146`, `526-527`.

**Cause:** v1 has no `mark_used`. The host writes `{used_qty, used_marked:1}` beside the sqlite store and `status`/`complete` read it. Runtime `used_qty`/`used_marked` stay 0 on that aggregate.

**Repro:** r1/build `stock-set BRK 5; open; reserve BRK 2; start`. r1/change `mark-used 0`. STATE_DIR gained `desk.usage.json` (`{"used_qty":0,"used_marked":1}`). Deleting that file made `status` report `used_marked:0` and `complete` return `usage_unmarked` even though the user had marked. Sidecar remains after a successful complete.

**Class:** application defect. Guidance (`build.md` step 2; brownfield: do not keep a sidecar as second authority) forbids it. CHANGE.md still asks for new usage rules on existing started jobs (guide clash, F14).

### F2. r2/change: `shop.used.json` same pattern (high, application)

**Where:** `src/desk.mjs:15`, `92-148`, `525-526`. Also leaves `shop.used.json.tmp` (write-to-tmp-then-write-dest, no unlink; observed after `mark-used`).

**Repro:** r2/build to `started`, r2/change `mark-used 0` created `shop.used.json` + `.tmp`. `status` showed `used_marked:1` from the overlay.

### F3. Host `shelf_json` is the amount authority in all four (medium, application)

Machines persist whatever JSON the host passes. `already_stocked`, `insufficient_stock`, reserve decrement, cancel restock, and leftover restock are not machine guards (r1 reserve `when` is only `payment != 1`; r2 `receive_stock` does not even bind sku/qty). A behavioral suite that only drives `./run` will still pass.

### F4. r1/change completed view depends on sidecar remaining (medium, application)

v1 `complete` is invoked with `used_qty: f.reserved_qty` (`559`), so the store records full consume. `applyUsageView` after complete still prefers the sidecar (`137-141`). If the sidecar is gone, completed + `used_marked==0` synthesizes `used_qty = reserved_qty` (`142-144`), which is the old-instance heuristic, not the leftover-restock truth.

## 3. Partial-commit seams

### F5. r2/change v1 complete is not a commit — it is `corrupt_state` (critical, application)

**Where:** `src/desk.mjs:553-563` calling `agg.transaction([{ name: "stock_set", args: {...} }, { name: "complete", args: { used_qty: used } }])`.

**Cause:** Kernel transaction steps must look like command bodies (`{command: {name, args}}` / observation). Passing `{name, args}` at the step root is `IK_PROTOCOL_INVALID`. Mapped to `corrupt_state`. Overlay is not cleared (`clearUsedOverlay` is after the throw). Job stays `started`.

**Repro:** pre-change started shop, change-stage `mark-used 1` (ok), `complete` → `{"error":"corrupt_state"}`. Same for `mark-used 0`. Direct probe on that store: `transaction([...])` raised `ProtocolError` `IK_PROTOCOL_INVALID`; a following `command("stock_set", ...)` succeeded. New v2 jobs (`mark-used 0` then `complete`) succeeded with `restocked_qty:3`.

CHANGE C3/C4 for **old started** instances is not delivered. Tests never create a v1 store, so they stay green.

### F6. r1/change v1 complete is two runtime commits (high, application)

**Where:** `src/desk.mjs:555-559`: `stock_set` (restock) then `complete`.

A crash after the first `apply` leaves `started` + restocked shelf + sidecar still marked. Retry computes `restocked_qty` again and `stock_set`s the same leftover onto an already-restocked shelf, then completes. No `CRASH_AT` label covers this seam; not live-crashed. Source sequence is two separate `agg.command` calls with no `transaction`.

### F7. Purchase: POST, then `recordEffectOutcome`, then `receive_stock` (medium, application; recovered by GET)

All four: `save_purchase` commits pending effect, `crash("after-purchase-saved-before-request")`, POST, `crash("after-accept-before-record")`, record + `receive_stock`, `crash("after-record-before-exit")`.

Crash after accept and before record is the specified R9 case; later `order-part` GETs the same id and does not POST if 200. That is the intended seam, closed by lookup.

r2 `maybeRecord` (`r2/build src/desk.mjs:258-267`, `r2/change:340-349`) **swallows** `recordEffectOutcome` errors and still `applyReceive`. Local stock can move while the pending effect remains. Next `order-part` sees `payment:"received"` and no-ops. Not a second POST, but the kernel effect and domain payment can diverge.

## 4. Operation / effect binding

### F8. Purchase POST is bound to the saved id; a second POST is possible after 404 (by spec)

`save_purchase` `when` is `payment == none/0`, so a second save cannot allocate a new id. After `attempt_saved`, `order-part` GET then POST **the same id** on 404 (r1 `516-517`, r2 `postSaved`). That is BRIEF R8, not a replacement id.

Kernel `command()` always mints a new operation id (none of the four pass `{operationId}`). Repeating `order-part` does not replay `save_purchase`.

### F9. No `lookupOperation` in any replica (low for BRIEF HTTP recovery; medium vs Ikaros record recovery)

`grep lookupOperation` over all `src/*.mjs`: no hits. Dropped **HTTP** replies are handled by GET `/v1/purchases/<id>` (BRIEF R9/R11). Dropped **kernel record** replies are not reconciled via `lookupOperation` (`docs/client-recovery.md`, `typescript.md` recording recipe). r1 lets record errors surface; r2 swallows them (F7).

## 5. Unknown outcomes

HTTP transport throw, incomplete body, and 5xx → `service_unavailable`, payment stays `attempt_saved`. Matching 200 → adopt. Mismatching 200 → `lookup_conflict` (no local receive). Reproduced paths in the delivered tests cover drop_reply / 5xx / reconcile `not_sent`.

### F10. r1 empty/unparseable HTTP 200 is `lookup_conflict` not `service_unavailable` (low, application)

`handlePostResult` (`r1/build src/desk.mjs:329-337`, same in change): status 200 + failed `purchaseMatch` (including `json == null`) is `lookup_conflict`. BRIEF lists incomplete response with `service_unavailable`. Stub drop_reply destroys the socket (likely fetch throw, not empty 200), so tests miss it.

### F11. r2 empty GET/POST body is always incomplete (low, application)

`httpJson` (`r2/build:204-207`): any empty `text` throws incomplete → `service_unavailable`. The shipped stub 404s with `{"error":"not_found"}`, so reconcile `not_sent` still works. An empty 404 body would never yield `not_sent`.

### F12. r2 kernel refusals become `corrupt_state` (medium, application)

`main().catch` (`r2/build:546-549`, `r2/change:693-696`) maps only `kernelError` (corrupt/store) then defaults to `corrupt_state`. Host pre-filters hide this. F5 is the visible case: protocol error from `transaction` is reported as `corrupt_state`.

r1 maps `classify() === "refused"` to `bad_status` (`r1/build:613-616`).

## 6. Persisted owner routing (change stage)

### What works

Both change programs keep `desk_v1.ik.toml` / `shop_v1.ik.toml` with the original `machine_id` / version 1. Discovery `show` through v2 on a v1 aggregate succeeded in probe (`owner.version === 1`, `spec_hash` `5adc3f8f…`). Commands then use the v1 handle (`routeMachine` / `ownerMachine`).

Old **completed** jobs: change-stage `status` reports `used_qty == reserved_qty`, `used_marked:1`, shelf unrestocked; `mark-used` is `already_completed`. Reproduced on both r1 and r2.

Old **started** jobs: `complete` is `usage_unmarked` until mark (r1 and r2). That part of CHANGE.md is honored.

### F13. r2/change cannot complete a v1 started job after mark (critical, application) — see F5

Owner routing finds v1; the v1 write path is the broken `transaction`.

### F14. Existing started instances cannot gain `mark_used` without a sidecar or a spec_hash change (candidate/guide)

Ikaros change journey: keep the previous definition; new `.ik.toml` is for **new** aggregates. CHANGE.md: started jobs with no mark follow the **new** `mark-used`/`complete` rules. v1 has `used_qty`/`used_marked` facts but no `mark_used` command. Both replicas used a sidecar (F1/F2). That is the forbidden “host saga / sidecar” close from `build.md` step 2.

r1/change tests call `/tmp/desk-pre-change-N10r1/run` for old instances; r2/change tests never construct a v1 store.

## 7. Hollow paths / unused rules / tests

### F15. r2 second reserve is `bad_status` not `already_reserved` (medium, application)

**Where:** `r2/build src/desk.mjs:387-391`; `r2/change:470-474`.

**Repro:** r2/build `stock-set PAD 4; open; reserve PAD 2; reserve PAD 1` → `{"error":"bad_status"}` (exit 1). Same on r2/change new v2 job.

BRIEF: “A second reserve is `already_reserved`.” r1 implements that (`r1/build:419`). r2 tests never second-reserve.

### F16. `ack_received` is unused in the r1 host (low, hollow)

`desk.ik.toml` / `desk_v1.ik.toml` `commands.ack_received` (`84-87`). No `ack_received` string in `src/desk.mjs`. Scenarios call it; the CLI never does. After `receive_stock`, payment is already 2.

### F17. r2 machine corpora are placeholders (low, hollow)

`machines/shop.ik.cases.json` (build and change) uses `"shelf_json": "example"`, `"name": "example"`, and i64 `boundary_min/max` args. Not witness cases for the desk. r1 cases are at least path-shaped.

### F18. r2 `command` success bodies ignore the returned aggregate for `open` (low)

`void next` after `open` (`r2/build:370-378`, `r2/change:453-461`) prints a hardcoded success object. Fine if `command` threw; misleading if a `HistoricalResult` were returned (r1 treats that as `corrupt_state`).

### Tests that would miss the serious defects

- r2/change tests only create **new** v2 instances: they never see F2/F5/F13.
- r2 tests never assert `already_reserved` (F15).
- r1/change old-instance tests pass **with** the sidecar (F1); they do not delete `desk.usage.json` or crash between the two v1 complete commits (F6).
- No test asserts that usage lives in sqlite rather than a JSON file.
- Callback tests only check ignore + unrelated bytes.

## 8. Disposable shadow-state check (the single edit)

| App | Single edit that keeps CLI behavior while dropping runtime as usage/lifecycle authority |
|---|---|
| r1/build | Host already computes every new `shelf_json` and error code from `show()`. Skipping `apply()`/`command` and answering from those host values works for the current process; durability still needs some store. The realistic durable bypass is the change-stage sidecar pattern: write `desk.json` and read it in `factsOf`. |
| r1/change | In `mark-used`, always `writeUsageSidecar` and never `apply(..., "mark_used")`. `status`/`complete` already prefer the sidecar (`applyUsageView`). Observed working for v1; would also shadow v2. |
| r2/build | Same host-blob pattern as r1/build. Plus second-reserve already never reaches a machine `already_reserved` rule. |
| r2/change | Always `writeUsedOverlay` and skip `mark_used`. `markView` reads the overlay for `started`. v2 `complete` still needs `used_marked==1` **in the machine** (`shop.ik.toml:65`), so a v2-only overlay bypass would then fail `complete` unless that guard is also skipped — v1 `complete` already does not use the machine for usage (and currently fails for another reason). |

The change-stage usage files are the live bypass: the app already works with them as a second authority.
