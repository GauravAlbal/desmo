## Verdict (short)

Build-stage writers on both replicas commit file / assess / approve / deny / appeal / save-payout / record-outcome / complete through the Ikaros store. Payout id is saved before POST. 5xx, dropped reply, and `CRASH_AT=after-payout-saved-before-request` leave `payment:"attempt_saved"` and retry the same id. Neither replica calls `lookup_operation` or passes a caller `operation_id`.

Change-stage owner routing works: a store created by the build binary `status`es and `approve`s under the change binary without `corrupt_state`. New files use v2 and keep salvage / denied_ms / payout amount in the runtime (no sidecar).

The family defect is **v1 shadow JSON as amount and deny-clock authority**. BRIEF: sidecars must not be the source of status after a mutating command. CHANGE: pre-change assessed/approved claims may `salvage`; a `deny` run under the change persists `denied_ms`. r1 writes `claim_v1_overlay.json` for salvage, denied_ms, and payout_amount and **reads those fields back as status**. r2 writes `claim.ext.json` for salvage and payout_amount, but a post-change `deny` on a v1 instance does **not** persist `denied_ms`, so C3's revised appeal window never opens. An unlabeled crash between `save_payout` and the sidecar write makes a later payout POST the **un-salvaged** approve amount.

In-repo tests never create a v1 store with the build binary and then run the change binary, so they miss F1–F4.

## 2. Duplicate authorities / shadow state

Build replicas have no host JSON sidecar. Change replicas do.

### F1. Change-stage JSON sidecar is the source of salvage / amount / (r1) denied_ms after mutating commands

**Where:**

- r1/change `OVERLAY_NAME` `claim_desk.py:28`; `write_overlay` `134-141`; `salvage_value` / `salvage_is_set` / `denied_clock` `221-247`; `status_obj` overlay `payout_amount` `256-268`; `do_salvage` v1 branch `672-675`; `do_deny` v1 branch `487-491`; `do_payout` v1 snapshot `552-555`.
- r2/change `EXT_NAME` `claim_desk.py:25`; `_save_ext` `186-195`; `_salvage_cents` / `_salvage_locked` / `_snapshot_amount` `293-321`; `_status_payload` `350-356`; `cmd_salvage` v1 branch `656-660`; `cmd_payout` v1 snapshot `762-774`.

**Cause:** v1 machines have no `salvage_*` command and no `denied_ms` fact. Hosts persist those fields in a second file and, after the command, **read the file to build status and the payout POST body**. BRIEF: "Application JSON sidecars must not be the source of status after a mutating command." `skills/ikaros/build.md` step 2 forbids a sidecar that decides lifecycle.

**Observed** (build binary `file`+`assess`, then change binary; scratch `STATE_DIR`):

- r1/change `salvage 300` → exit 0, `salvage_cents:300`. Files: `kernel.sqlite`, `claim_v1_overlay.json` with `{"salvage_cents":300}`. `status` reports `salvage_cents:300` from the overlay (`fact` has no such key on v1).
- r1/change `deny` at `NOW_MS=2000` → overlay `{"denied_ms":2000}`; `status.denied_ms` is 2000.
- r2/change `salvage 50` → `claim.ext.json` `{"salvage_cents":50,"salvage_set":1}`; `status.salvage_cents` is 50. Files: `claim.sqlite`, `claim.ext.json`.
- Contrast: a **new** file under the change binary (v2) writes no overlay/ext (r1: `kernel.sqlite` only; r2: `claim.sqlite` only).

**Divergence recipe:** `salvage 300`, delete the sidecar, `salvage 400` → exit 0 `salvage_cents:400`. Runtime store never knew 300. Reproduced on both change replicas.

**Severity:** high (BRIEF sidecar rule; C1/C2/C4 durability). **Class:** application defect. There is also a **candidate/guide tension**: CHANGE C1–C3 require new durable facts on instances that must keep the v1 `(machine_id, version, spec_hash)`, and that v1 spec cannot hold them. Sidecars are still the forbidden way to close that gap.

### F2. r1 v2 (and r1/build) appeal deadline is a host branch; machine `when` is only `appeal_used`

**Where:** r1/build `claim_desk.py:393-397` and `machines/claim_desk.ik.toml:48-53`; r1/change host `495-514` and v2 `machines/claim_desk.ik.toml:52-57` (`when = 'appeal_used == "0"'`). r1/change v2 `deny` writes `denied_ms` (`46-50`) but appeal does not compare `now_ms` to it.

**Cause:** deleting the host `if now_ms > deadline` check lets a closed appeal commit. r2 v2 encodes `$now_ms <= deadline_ms` on appeal and rewrites `deadline_ms` on deny (`r2/change machines/claim_desk.ik.toml:53-58, 60-65`).

**Severity:** medium. **Class:** application defect (host status branch).

## 3. Partial-commit seams

Labeled seams match the brief on all four writers:

1. `save_payout` commit, then `after-payout-saved-before-request`, then POST.
2. HTTP 200, then `after-accept-before-record`, then `record_effect_outcome` + `complete_payout`.
3. Those two kernel commits, then `after-record-before-exit`.

Observed on r1/build: SIGKILL at (1) → `payment:"attempt_saved"`, zero effects; later `payout` POSTs the same id and pays once. 5xx POST → `service_unavailable`, `attempt_saved`, effects 0; retry same id, one effect. Dropped-reply tests in-repo (not re-run as SIGKILL of an already-recorded pay).

`record_effect_outcome` then `complete_payout` are two kernel commits with no crash label between them. Death there leaves a recorded effect and `paying`/`payout_saved`; later GET 200 skips record when `pending_intent` is None and completes. Not reproduced as a labeled crash.

### F4. Unlabeled crash between v1 `save_payout` and sidecar snapshot → POST of the un-salvaged amount

**Where:** r1/change `551-555` then `560-567`; r2/change `762-774` then `_amount` `375-385` (payout_saved prefers `amount_cents` fact, which on v1 is the approve amount).

**Cause:** `CRASH_AT=after-payout-saved-before-request` runs **after** the sidecar write, so in-repo crash tests keep the snapshot. A death between the runtime commit and `write_overlay` / `_save_ext` is unlabeled. Recovery then POSTs `fact(amount_cents)` (approve, no salvage).

**Observed** (scratch copy with an extra `CRASH_AT=after-runtime-before-overlay` inserted only in `/tmp`, original writers unchanged):

- r1 v1 store: salvage 300 (payable 8000). Crash after `save_payout`. Overlay still `{"salvage_cents":300}` (no `payout_amount`). Status `attempt_saved`, `amount_cents:8000`. Retry `payout` → paid **8000**; provider effect `amount_cents:8000`. C4 requires 7700.
- r2 v1 store: salvage 50 (payable 400). Crash after `save_payout`. Ext still salvage only. Retry `payout` → paid **400**; effect 400. C4 requires 350.

**Severity:** high for C4/C5 on pre-change instances. **Class:** application defect. Behavioral tests would miss it: they only SIGKILL at the labeled point after the sidecar write.

r1/change v1 `deny` has the same two-step split (`487-491`: machine `deny` then overlay `denied_ms`). Death between them leaves `status:"denied"` with `denied_ms:null`, so appeal uses `filed_ms + window` (C3 miss). Not SIGKILL-reproduced; same structure as F4.

## 4. Operation / effect binding

### What holds (all four)

- First `payout` mints an id, commits it as effect `id` / `idempotency_key`, POSTs `{payout_id, claim_id, amount_cents}`, never allocates a replacement id.
- Saved-id retry GETs first; POST only on 404.
- `reconcile` never POSTs. 404 → `{lookup:"not_sent", payment:"attempt_saved"}`.
- Repeat `payout` after paid is a no-op with no extra effect (r1/build 5xx-then-retry: same id, effects 1).

### F5. No kernel `operation_id` / `lookup_operation`

None of the four `claim_desk.py` files call `lookup_operation` or pass `operation_id`. Lost stdout after a kernel commit is recovered by `show` + saved `payout_id`, not by `docs/client-recovery.md`.

The brief's payout recovery is provider GET by saved id, which they implement. The gap is kernel-commit attribution (`file`, `assess`, `complete_payout`).

**Severity:** medium for kernel lost-reply; low for the payout effect. **Class:** application vs guide.

## 5. Unknown outcomes

Provider: urllib throw, incomplete 200 body, HTTP 5xx → `service_unavailable`; local state stays `attempt_saved`. They do not mark `paid` from a timeout. GET 404 on reconcile is `not_sent`. urllib `HTTPError` 404 (including empty body) returns status 404 before r1's "GET with no JSON" guard, so a 404-then-POST recovery works even with an empty body (exercised against a scratch empty-404 stub: r1 and r2 both POSTed once and paid).

r1 `payout_matches` does not require `outcome:"paid"`; r2 `_parse_paid_body` does. Stub always sends `outcome:"paid"`. **Severity:** low.

## 6. Persisted owner routing (change stage)

Guidance: keep v1 loadable; route by `aggregate.owner`; new creates use the new definition (`skills/ikaros/change.md` step 5a). CHANGE.md: existing denials with `denied_ms:null` keep `filed_ms + appeal_window_ms`; a **deny run under the change** persists `denied_ms` and uses `denied_ms + appeal_window_ms`. Pre-change assessed/approved may `salvage`.

### What holds

- r1/change and r2/change `status` + `approve` on a store created by the matching build binary: assessed facts intact, no `corrupt_state`.
- Pre-change **already-denied** rows: both change binaries refuse appeal past `filed_ms + window` and allow it at the deadline. r1 overlay is not created. Matches the "existing persisted denials" sentence.
- New v2 files: r2/change `deny` at 1000, `appeal` at 5101 (past filed window 5100, inside denied+5000=6000) → assessed. r1/change v2 `deny` at 2000, `appeal` at 2005 (past filed 1010) → assessed.

### F3. r2/change post-change `deny` on a v1 instance does not persist `denied_ms`; appeal stays on the file clock

**Where:** `cmd_deny` v1 branch `574-575` (`command("deny")` only); v1 machine deny has no args (`machines/claim_desk_v1.ik.toml:50-52`); `cmd_appeal` `601-607` uses `_fact(denied_ms)` else `filed_ms + window`; v1 appeal `when` includes `$now_ms <= deadline_ms` from **file** time (`claim_desk_v1.ik.toml:54-58`). `_status_payload` prints `_fact(denied_ms)` (`351`) — always null on v1.

**Cause:** CHANGE C3: "When `deny` runs under this change it persists `denied_ms`". r2 does that only for `owner.version == 2`. A pre-change assessed claim denied after the upgrade is a new denial on an old owner. r1 implements that case via overlay (F1). r2 does not implement it at all.

**Observed** (r2/build `file` at 100 window 5000, `assess`; r2/change `deny` at 1000):

- `status.denied_ms` is `null`. No `claim.ext.json`.
- `appeal` at 5101 → `{error:"appeal_closed"}`.
- `appeal` at 6000 (the C3 deadline `1000+5000`) → `{error:"appeal_closed"}`.
- Contrast: same times on a v2 file → `denied_ms:1000`, appeal at 5101 succeeds.

**Severity:** high for C3 on existing assessed instances. **Class:** application defect.

## 8. Single edit that keeps the app working while bypassing the runtime

**Change replicas (already true for v1 salvage):** in `do_salvage` / `cmd_salvage`, keep only the overlay/ext branch (delete the `is_v2` `command(...)` arm). `salvage_value` / `_salvage_cents` already treat the JSON file as status after that mutation. Payout offset and `salvage_locked` keep working with **zero** Ikaros commits for salvage. That is the v1 path today (`r1/change:672-675`, `r2/change:656-660`).

**Build replicas:** host already decides appeal-closed, payable `min(limit, assessed)`, and named-status refusals. Replacing `apply_cmd` / `create_with` (r1) or `_settle`+`create_with` (r2) with a JSON put/get that `status_obj` reads would leave the CLI shape intact because those helpers are the only runtime writes; the machine `when`s are duplicated in the host.

## 9. Delivered defects a behavioral test would likely miss

- Sidecar vs runtime split (F1, F4): happy-path salvage+payout on **v2** (what the tests run) never creates the JSON file. Labeled `CRASH_AT=after-payout-saved-before-request` fires after the sidecar write, so crash tests keep the salvaged snapshot.
- r2 C3 on a v1 assessed→deny (F3): deny-clock tests `file` with the change binary.
- Deleting `claim_v1_overlay.json` / `claim.ext.json` unlocks a second salvage amount (runtime never locked). No test asserts the sqlite facts after salvage on a v1 store.
- Host-only appeal clock on r1 v2 (F2): tests always go through the host.
- `lookup_operation` unused (F5): lost stdout after `complete_payout` is not in the suite.
