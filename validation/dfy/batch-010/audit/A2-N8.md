## Verdict (short)

Both replicas commit open / save-attempt / effect-record / adopt / cancel / expire through Ikaros and bind `POST /v1/charges` to a charge id saved before the request. Neither uses `lookupOperation` or a caller `operation_id`. There is no host sidecar file; one aggregate, one store.

The main lifecycle defect is **host retry accounting that treats a pre-POST `save_charge`/`save_attempt` as a consumed attempt**. On r1 (build and change), `renew` after `CRASH_AT=after-charge-saved-before-request` with `retry_limit=1` returns `retry_exhausted` and never POSTs the saved id. r2 POSTs that same id and becomes `paid`. The in-repo crash tests use `retry_limit=3`, so they do not see this.

Change-stage owner routing works on both replicas for v1 `status`/`cancel`. C3 revised grace on a **new** v2 instance works on both. On a **persisted v1** store, r1/change still expires at `renewal_ms + grace_ms` (C3 miss). r2/change applies the new deadline in the host, but v1 `adopt` does not clear `first_failure_ms`, so the next cycle expires a paid subscription.

This family is a fit for one Ikaros aggregate plus an effect. Builders did not need a saga. Remaining misses are host status branches and change-stage fact clearing, not topology.

## 2. Duplicate authorities / shadow state

No `desk-aux.json` and no second SQLite file. Shadow state is host interpretation of facts the machine already stores.

### F1. r1 (build and change): host `attempts >= retry_limit` before POSTing a never-sent saved id

**Where:** r1/build `src/main.mjs:478-496`; r1/change `src/main.mjs:571-581`. Machine: `save_charge` `attempts = "+1"` then effect (`machines/subscription.ik.toml:39-45`).

**Cause:** `save_charge` commits in `active` → `past_due` and increments `attempts` *before* `CRASH_AT=after-charge-saved-before-request`. Later `renew` sees a saved id, GETs 404, then:

```
if (attempts >= limit) fail("retry_exhausted");
agg = await execCmd(agg, "count_retry", ...);
await postSaved(...)
```

`attempts` is used as a POST count. A crash before the first POST already has `attempts == retry_limit` when the limit is 1, so the host never POSTs the saved id. R8 requires that later renew POST that same id.

**Observed** (`./run`, not a unit mock):

- Command: `renew`. Start: `past_due`, `payment:"attempt_saved"`, `attempts:1`, `retry_limit:1`, `first_failure_ms:null`, charge id present, zero provider effects.
- Produced: `{ "error": "retry_exhausted" }`. Status unchanged. Effects unchanged.
- Discriminator: identical sequence with `retry_limit:3` → `paid`, one effect (r1/build). r2/build and r2/change with `retry_limit:1` → `paid`, one effect.

**Severity:** high (R8). **Class:** application defect. r2’s 404 path only exhausts when `first_failure_ms` is set (`r2/change src/main.js:625-626`), which is the mapping that keeps a pre-POST save retryable.

### F2. Host due / grace / retry vs machine `when`

**Where:** r1/build `cmdRenew` `468-507`; r2/build `renew` `445-471`; r1 `expire` has `now_ms` but no `when` (`subscription.ik.toml:68-71`); r2 `save_attempt` has no clock (`subscription.ik.toml:51-57`).

**Cause:** `not_due`, `grace_elapsed`, and `retry_exhausted` are host branches. r1 `save_charge` does encode `now_ms >= renewal_ms && attempts < retry_limit`, but the host returns domain codes without submitting when those guards would refuse (`mapKernelErr` would otherwise emit `refused`). r2’s save command cannot refuse a post-grace charge at all.

**Observed:** `renew` at `NOW_MS=5` on renewal 10 → `not_due` (r1/build). First `renew` at `NOW_MS=20` with grace 5 → `grace_elapsed` and status `expired` (r1 and r2).

**Severity:** medium. **Class:** application defect (host status branch). The brief’s clock rules can live on the machine; r1 already has a partial `when` for due/retry.

### F3. r2 `payment` fact vs named state

**Where:** r2 machines `payment` replace-fact; host `viewStatus` prints `f.payment` and `named(agg)` separately.

**Cause:** `expire` does not clear `payment`. After F8 below, status can be `expired` with `payment:"paid"`.

**Severity:** low by itself; high when combined with F8. **Class:** application defect.

## 3. Partial-commit seams

Intended seams match the crash labels:

1. `save_*` commit, then `after-charge-saved-before-request`, then POST.
2. HTTP 200, then `after-accept-before-record`, then `recordEffectOutcome` + adopt/`complete`.
3. Adopt commit, then `after-record-before-exit`.

Observed: crash at (1) leaves `past_due`/`attempt_saved` and zero effects (r1 and r2). Dropped reply leaves `service_unavailable` + `attempt_saved`; `reconcile` of that charge id returns `lookup:"paid"` with effects unchanged (r1/build and r2/build). Crash at (3) is covered by in-repo tests (not re-run here as a SIGKILL of an already-paid record).

No extra host file between kernel commits. The remaining split is HTTP vs kernel, which the brief requires.

`recordEffectOutcome` then `complete`/`adopt` are two kernel commits with no crash label between them. A death there leaves a recorded effect and `past_due`; later GET 200 + adopt is the recovery the host already runs. Not reproduced as a labeled crash.

## 4. Operation / effect binding

### What holds

- First due `renew` mints a charge id, commits it as effect `id` / `idempotency_key`, POSTs that snapshot, never allocates a replacement id.
- Saved-id retry GETs first; POST only on 404 (when the host does not refuse first).
- `reconcile` never POSTs. Dropped-reply then reconcile: `lookup:"paid"`, effect count unchanged.
- Repeat `renew` after paid (r1 `active_paid`; r2 `payment=="paid" && now < cycle`): no extra effect.

### F4. No kernel `operation_id` / `lookupOperation`

None of the four `src/main.*` files call `lookupOperation` or pass `operationId` into `createWith` / `command` / `execute` / `recordEffectOutcome`. Lost stdout after a kernel commit is recovered by `show` + saved `charge_id`, not by `docs/client-recovery.md`.

The brief’s card-effect recovery is provider GET by saved charge id, which they implement (except F1). The gap is kernel-commit attribution (`open`, `cancel`, `complete`/`adopt`).

**Severity:** medium for kernel lost-reply; low for the card effect when F1 does not fire. **Class:** application vs guide.

### F5. r1 outcome digest is SHA-256 of the HTTP body; r2 hashes `JSON.stringify(json)`

Both bind *some* digest of the provider response. r1 uses the raw text (`digestBody`). Not a second effect. **Severity:** low.

## 5. Error and unknown outcomes

Provider: fetch throw, incomplete body, HTTP 5xx → `service_unavailable`, state stays `attempt_saved`. They do not adopt `paid` from a timeout. GET 404 is `not_sent` on `reconcile` (r1 `cmdReconcile`; r2 same). Stub 404 body is JSON `{error:"not_found"}`, so r2’s empty-body `incomplete` path does not misfire.

### F6. Refusal-code mapping

| Start | Command | r1 produced | r2 produced |
|---|---|---|---|
| `active`, now before renewal | `renew` | `not_due` | `not_due` |
| `expired` | `renew` | `expired` | `grace_elapsed` |
| `expired` | `cancel` | (not hit in r1 after expire-on-renew) | `cancelled` |
| `cancelled` | `cancel` | `cancelled` | `cancelled` |
| `cancelled` | `renew` | `cancelled` | `cancelled` |
| `past_due` + charge | `cancel` | `charge_started` | `charge_started` |

r1 distinguishes a second post-grace `renew` (`expired`) from the first (`grace_elapsed`). r2 maps both to `grace_elapsed`, and maps cancel-of-expired to `cancelled`. Host intercepts named state before `execute`, so r2’s `mapKernel` → always `corrupt_state` (`src/main.js:121-125`) was **not** the code on these paths.

**Severity:** low for the expired/cancelled aliases (still refusals, no mutation). **Class:** application defect (mapping). The `mapKernel` collapse is a latent mapping: any leaked `IK_ILLEGAL_STATE` becomes `corrupt_state`. Not observed on the CLI paths above.

## 6. Persisted owner routing (change stage)

Guidance: keep v1 loadable; route by `aggregate.owner`; do not command an old aggregate through the new machine (`skills/ikaros/change.md` step 5a). CHANGE.md: revised grace applies when an existing instance with `first_failure_ms:null` next fails; successful renew clears the marker.

### r1/change — routes by owner; C3 deadline is version-gated

`retryDeadline` (`238-243`): `first_failure_ms + grace_ms` only if `machineVersion >= 2`. v1 keeps `renewal_ms + grace_ms`. `downgrade` on v1 is `refused` (`465`) without sending v2 `downgrade`.

**Observed** (r1/build `open`, then r1/change `./run` on the same `STATE_DIR`):

- `status` → `active`, v1 facts intact (no `corrupt_state` / `IK_MACHINE_MISMATCH`).
- `downgrade sub1 pro` → `{ "error": "refused" }`.
- `cancel` → `cancelled` via v1 `cancel`.

**Observed C3 on a new v2 instance** (`open` with change binary, renewal 10, grace 20, fail POST at NOW=12, then NOW=31): `service_unavailable` with `first_failure_ms:12`, then `paid`. Old deadline 30, revised 32. Matches C3.

**Observed C3 on a v1 store** (build `open`, change binary for the failed POST and later `renew`):

- Command: `renew` at NOW=31. Start: v1 `past_due`, `attempt_saved`, `first_failure_ms:12`.
- Produced: `{ "error": "grace_elapsed" }` (then NOW=33 → `expired`).
- Owner of the decision: host `retryDeadline` ignoring `first_failure_ms` when version is 1, then `expire`.

### F7. r1/change does not apply revised grace to existing instances

CHANGE.md: existing rows acquire `first_failure_ms` on the next failed attempt; the retry deadline becomes `first_failure_ms + grace_ms`. r1 records the field on v1 (`note_failure` exists on v1) and then expires using the old deadline anyway.

**Severity:** high for C3 continuity. **Class:** application defect (host version branch). Not a machine-identity mismatch.

### r2/change — routes by owner; C3 deadline is host-wide; v1 adopt does not clear the marker

v1 `downgrade` → `{ "error": "bad_args" }` (`src/main.js` identity check against v1). v1 `status` after build `open` works.

**Observed C3 on v1 store:** fail at NOW=12, `renew` at NOW=31 → `paid`. Host `graceDeadlineMs` (`216-223`) uses `first_failure_ms` regardless of owner version.

### F8. r2/change v1 `adopt` leaves `first_failure_ms`; next cycle expires a paid row

**Where:** `adoptPaid` `296-302` adds `first_failure_ms: 0` only for `owner.version === 2`. v1 `adopt` in `subscription_v1.ik.toml` has no those args.

**Observed:**

- After fail+paid on a v1 store: status `active`, `payment:"paid"`, `first_failure_ms:12`, `renewal_ms:2592000010`.
- Command: `renew` at `NOW_MS=2592000010` (the new due instant). Start: that paid active row.
- Produced: `{ "error": "grace_elapsed" }`. Status `expired` with `payment:"paid"` still set.
- Contrast: same sequence on a v2 instance charges a new cycle (`renewal_ms:5184000010`, `first_failure_ms:null`).

Paid no-op is `payment === "paid" && nowMs < cycle` (`r2/change src/main.js:548-550`), so NOW=100 (still before the new cycle) still no-ops. The discriminator is the **next due instant**, where `nowMs < cycle` is false and `graceDeadlineMs` uses the leftover 12+20=32.

**Severity:** high for existing-instance C3/C4. **Class:** application defect (adopt args / host deadline). CHANGE requires a successful renew to clear the failure marker.

## 7. Hollow paths / unused rules / weak tests

### F9. In-repo crash tests never use `retry_limit=1` on a saved-id retry

r1 `test/ledger.test.mjs` crash recover and r2 `tests/app.test.js` crash recover open with `"3"`. r2’s `retry_limit=1` cases are grace-elapsed without a saved id, or exhaust after a recorded failure. F1 is therefore untested, not flaky.

r1/change C3 test (`test/ledger.test.mjs` “revised grace uses first_failure_ms”) only `open`s with the change binary (v2). No v1 continuity case. r2/change tests likewise do not create a v1 instance with the pre-change binary then fail+pay+next-cycle.

### F10. Corpora are type-valid placeholders

r1 `machines/subscription.cases.json` / `subscription_v2.cases.json` and r2 `subscription.ik.cases.json` are single `ok` rows. Scenarios walk `open` → `save_*` → `complete`/`adopt` without HTTP or crash labels. Not hollow assertions, not the R8/C3 seams.

### F11. r1 `active_paid` has no second-cycle `save_charge`

`complete` → `active_paid`; `save_charge` is `from = ["active"]`. Repeat `renew` is a host no-op on `active_paid` even at the advanced `renewal_ms`. Brief R5 (“repeat renew after paid is a no-op”) is satisfied; a later 30-day cycle cannot charge. r2 v2 can. Not scored as a fail of R5.

r1 `count_retry` is used (404 path). r2 `retry_post` is used only when `first_failure_ms` is set. r1 `note_failure` is used on POST fail / drop. No command was found that returns exit 0 without a runtime commit on a mutating happy path except paid no-op / same-plan downgrade.

## 8. Disposable shadow-state check

What single edit would keep the happy path appearing to work while bypassing the runtime:

**r1 (build and change).** The crash tests would still pass if `retry_limit` stays 3. The disposable lie for F1 is already in production code: host `retry_exhausted` on `attempts >= limit` after a save that never POSTed. Skipping `expire` and only printing `grace_elapsed` would fail the tests that `status` `expired`. Skipping the host `pastGrace` check and calling `save_charge` would still commit after grace (machine `when` is only `now >= renewal`). That host grace check is the real due-authority.

**r2 (build and change).** Skip `if (nowMs > deadline) expire` and `save_attempt` still has no clock; a post-grace `renew` would POST. Occupancy-style sidecar is not needed. The v1 leftover `first_failure_ms` is already enough to expire a paid row at the next due instant without editing source.

## Candidate vs application (cross-cutting)

- **Application:** F1 (r1 only; r2 independently POSTs the saved id). F7 (r1/change version-gates C3). F8 (r2/change v1 adopt args). Host due/grace. Hollow crash/`retry_limit` coverage.
- **Application vs guide:** no `lookupOperation`; due/grace could be machine `when` (r1 already has a partial one).
- **Not a candidate/topology miss:** one aggregate, one store, effect id = charge id. `build.md` step 2 fit-refusal does not apply. Change-stage `Aggregate.owner` routing is implemented on both replicas.
- **Shared transition for F1:** `save_charge`/`save_attempt` increments `attempts` in `active` → `past_due` before POST. r1’s later `renew` treats that counter as “POSTs used.” r2’s later `renew` treats “POST used” as `first_failure_ms` set. Same start state, two mappings, two outcomes. Not timing.
