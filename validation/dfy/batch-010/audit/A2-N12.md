## Verdict (short)

None of the four apps keep lifecycle in a host sidecar file. Durable facts live in one Ikaros sqlite per desk. SMS `POST /v1/notices` is preceded by a kernel command that plans `effect.kind = "sms.notice"` with `id` / `idempotency_key` equal to the saved notice id (`begin_notice` on r1, `prepare_sms` on r2). Lost HTTP replies and 5xx leave `notice:"attempt_saved"` and recover the **same** notice id.

They still do **not** treat the runtime as the only authority:

- Roster, overlap, fullness, era, buddy, and swap-hold are decided in host JavaScript. The machine commands (`post_shift` / `replace_roster` / `offer_swap`) accept whatever JSON or field values the host computed.
- No replica calls `lookupOperation`. `command()` mints a fresh operation id every time.
- **r1/build is unusable**: `package.json` is not JSON (leaked tool-warning trailer). Node 22 raises `ERR_INVALID_PACKAGE_CONFIG`. Source was inspected; `./run` was not exercised.
- **r1/change** never versions the machine and never reads `Aggregate.owner`. New lifecycle (`confirm-swap`, era:2 accept-without-SMS, `swap_hold`) is host-only. Repeating an earlier successful assign is `already_assigned` instead of a no-op. A completed `accepted` swap permanently blocks `offer-swap` (`swap_open`).
- **r2/change** does route by `agg.owner` and keeps v1. That path works for a **first** pre-change pending swap (`era:1`). It fails for a pre-change **second** swap (`era:2` from the build-stage counter): `respond-swap accept` returns `bad_args` and the swap stays pending. `confirm-swap` while an unrelated callout is `attempt_saved` reports success, assigns the callout, and never exchanges or sends the swap SMS.

## 1. Named writer paths

No replica writes a JSON overlay / aux / usage sidecar. Unrelated `STATE_DIR` bytes are left alone (tests and r1/change smoke: `keep.bin` / `unrelated.txt` pattern in tests). The only durable file is the Ikaros store.

### r1/build (source only; process will not start)

Writers in `src/desk.mjs`: `machine.createWith` open; `agg.command` for `post_shift`, `cancel_shift`, `offer_swap`, `decline_swap`, `expire_swap`, `begin_notice`, `commit_sent`. SMS is `fetch` POST/GET.

`package.json` bytes are a valid object **plus** extra text (see finding F1). `./run` execs `src/desk.mjs`; Node refuses the package config before any command runs.

### r1/change

Same writer set, plus host command `confirm-swap`. Era:2 `respond-swap accept` does **not** introduce a machine command: it overwrites `swap_json` through `offer_swap` (`src/desk.mjs:616-619`). Confirm persists buddy inside `swap_json` via `commit_sent`, not a `set_buddy` command. The machine file is still `machine_version = 1` with no confirm/hold/buddy facts (`machines/desk.ik.toml`).

### r2/build

Writers: `createWith` open; `replace_roster` / `replace_roster_pending`; `offer_swap`, `decline_swap`, `expire_swap`; `prepare_sms` (plans the effect); `commit_sms`; `recordEffectOutcome` when `pendingIntent` is present (`src/desk.mjs:260-277`, `318-336`).

### r2/change

Same, plus `accept_swap` and `set_buddy` on v2 only (`machines/desk.ik.toml:70-82`). `bindExisting` (`src/desk.mjs:216-226`) shows through v2, then opens v1 when `!agg.owner.equals(m2.identity)`. ## 2. Duplicate authorities / shadow state

**Finding F2 — host blob is the roster authority (all replicas).** Class: application defect. Severity: high.

The kernel stores an opaque snapshot the machine does not interpret.

- r1: facts `shifts_json`, `assignments_json`, `swap_json`. Commands `post_shift` / `offer_swap` / `expire_swap` take the host string with no overlap/full/era/`when` guard (`machines/desk.ik.toml:32-70`). Host parsers at `src/desk.mjs:97-124` (build and change).
- r2: fact `roster` is a JSON string of shifts/volunteers. `replace_roster` writes it verbatim (`r2/build/src/desk.mjs:440-445`; change: `479-484`). Swap **fields** are typed, but overlap, slots, and hold remain host `if`s (`r2/change/src/desk.mjs:537-553`).

Status on r2 reads `shift_count` / `assignment_count` facts, not a recount of `roster`, so those two encodings can diverge if a writer updates one.

Ikaros build rule: no host branch may decide the same lifecycle; a host saga or host status branch makes the host a second authority (`skills/ikaros/build.md` step 8 / fit rule).

**Finding F3 — r1/change new lifecycle is not in the machine.** Class: application defect. Severity: high.

CHANGE.md requires era:2 accept without SMS, `confirm-swap`, `swap_hold`, `legacy_swap`. None of those commands or guards exist in `r1/change/project/machines/desk.ik.toml` (still v1, same as build). Host functions `swapHolds` (`src/desk.mjs:244-246`), `cmdRespond` era branch (`616-619`), `cmdConfirm` (`765-831`) decide them. `Aggregate.owner` is never read.

## 3. Partial-commit seams

Crash labels are implemented with `SIGKILL` after the matching durable step.

| Label | r1 | r2 |
|---|---|---|
| `after-notice-saved-before-request` | after `begin_notice`, before POST (`desk.mjs:405`) | after `prepare_sms`, before POST (`sendNewSms`) |
| `after-accept-before-record` | after POST 200, before `recordAndCommit` | first line of `recordAndCommit`, before `recordEffectOutcome` / `commit_sms` |
| `after-record-before-exit` | after `commit_sent` | after `commit_sms` |

HTTP 5xx / drop / timeout: both r1/change and r2/change leave `attempt_saved` and do not guess `sent`. Scratch: r1/change POST 500 then later assign recovered the **same** notice id (one stored effect after GET 404 + POST). r2/change POST 503 same pattern.

**Finding F4 — r2 `confirm-swap` treats any pending SMS as “confirm succeeded”.** Class: application defect. Severity: high.

`r2/change/project/src/desk.mjs:708-720`: if `pending_sms === 1`, `recoverSms` runs and the command prints confirm success with `rec.snap.notice_id`, without checking `kind === "swap"` or exchanging assignments.

Reproduction (scratch, r2/change `./run`):

1. Open, post `a,b,c`, assign `v1,v2,v3`, `offer-swap` / `respond-swap accept` (era:2, no SMS).
2. `CRASH_AT=after-notice-saved-before-request ./run assign c v4` (exit 137). Status: `notice:"attempt_saved"` for v4/c callout; swap `accepted`; `buddy_id` null.
3. `./run confirm-swap sw v3` → `{status:"accepted", buddy_id:"v3", notice:"sent", notice_id: <v4 callout id>}`.
4. Status: `assignments:4` (v4 now placed), `buddy_id` still null, swap not exchanged. Provider effects: callout for v4 only; no `kind:"swap"`.

A behavioral test that only confirms on a clean accepted swap (r2 change `tests/desk.test.mjs` “era2 confirm-swap buddy and swap_hold”) does not see this.

**Finding F5 — r1/change confirm vs unrelated `attempt_saved` is stuck `lookup_conflict`.** Class: application defect. Severity: medium.

`adoptOrPost` (`src/desk.mjs:363-370`) refuses if a saved attempt’s fields do not match the confirm snapshot. Same crash-assign-then-confirm recipe on r1/change returned `lookup_conflict` and left the accepted swap unconfirmed (notice still the callout attempt). Confirm cannot proceed until some other command finishes that attempt. Not hollow, but one global notice slot couples unrelated commands.

**Finding F6 — r2 `set_buddy` commits before `prepare_sms`.** Class: application defect. Severity: low.

`r2/change/src/desk.mjs:722-733`: `set_buddy` is a separate command, then a **new** `newNoticeId()` and `sendNewSms`. A kill between them leaves `buddy_id` persisted with `pending_sms=0`. Retry allocates a different notice id (no POST yet, so no double effect). There is no `CRASH_AT` in that window.

## 4. Operation / effect binding

Planned effect id = notice id = POST body `notice_id` on both replicas that run. A 404 lookup POSTs that saved id only (r1 `adoptOrPost` pending branch; r2 `recoverSms` 404 branch). Same-id provider POST is idempotent.

Neither replica passes `operationId` into `command()` / `createWith`. A lost **kernel** reply cannot be asked via `lookupOperation` (zero matches under N12 `*.mjs`). Next user command uses `show` and domain notice state. That is enough when `show` sees the commit; it is not the client-recovery matrix (`docs/client-recovery.md`).

**Finding F7 — one `assign` can complete a saved attempt and issue a second SMS.** Class: application defect. Severity: medium.

r2 `assign` (`src/desk.mjs:523-561` change; same structure in build `484-524`): if `pending_sms===1` and the saved snap is a **different** pair, it still `recoverSms` (POST if 404) then allocates `newNoticeId()` and `sendNewSms` for the requested pair.

Reproduction (r2/change): crash-save assign `a v3`; then `assign b v2` succeeded. Effects included both v3/a and v2/b. Status `assignments:3`. BRIEF: a saved attempt is looked up / POSTed with the saved id and must not allocate a replacement id **for that attempt**; the extra new attempt in the same invocation is host compounding.

r1 instead `lookup_conflict`s when the saved snap is not this pair (`cmdAssign` `537-541`), which avoids the second POST but also blocks the new assign until reconcile.

**Finding F8 — r1 `command()` timeout maps to `corrupt_state`.** Class: application defect. Severity: medium.

`mapKernel` (`r1/*/src/desk.mjs:159-165`) handles `StoreNotFoundError`, `corrupt`, `not_found`; anything else including `uncertain` becomes `corrupt_state`. That guesses a damaged store after a transport-unknown kernel call. r2 maps `uncertain` → `service_unavailable` (`mapKernelError` `175-182`).

## 5. Unknown outcomes (HTTP)

Exercised:

- Dropped 200 reply (r1/change tests; r2 tests): `service_unavailable`, `attempt_saved`, reconcile GET 200 adopts `sent`, no second effect.
- HTTP 5xx (scratch, r1/change 500 and r2/change 503): first invocation `service_unavailable` + `attempt_saved`; later assign GET 404 then POST same id, one stored effect.
- Incomplete body / timeout: r1 `postNotice` empty/non-JSON → `service_unavailable` (`413-414`); r2 `httpJson` `incomplete`/`fail` → `service_unavailable` (`332-333`). They do not mark `sent`.

r2 POST 200 with mismatched body is `lookup_conflict` **after** `prepare_sms` already committed (`335-368`). Local state did change (`attempt_saved`); the error name is the lookup term. Next assign recovers. Severity: low.

## 6. Persisted owner routing (change stage)

CHANGE.md old-instance policy is **swap `era`**, not desk identity: pre-change swaps keep `era:1` and still complete on `respond-swap accept`; post-change swaps persist `era:2` and need `confirm-swap`.

### r1/change

No machine version bump, so `owner` routing is unused. `offer-swap` always writes `era: 2` (`src/desk.mjs:578-587`). A pending `era:1` record still in `swap_json` is honored (`cmdRespond` only skips SMS when `Number(swap.era)===2`; `cmdConfirm` `legacy_swap` when era≠2). Tests inject era:1 by calling `offer_swap` with JSON (`tests/desk.test.mjs:254-271`), not by running r1/build (which cannot start).

### r2/change

`bindExisting` + retained `desk.v1.ik.toml` is the documented `Aggregate.owner` pattern. Scratch: a store created by r2/build (`era:1` pending) then r2/change `status` / `confirm-swap` → `legacy_swap` / `assign` of counterpart to another shift succeeded / `respond-swap accept` sent swap SMS. C3/C4 for **first** pending swap hold.

**Finding F9 — post-change swaps on a v1 desk are `era:1`, not `era:2`.** Class: application defect. Severity: medium.

`offer-swap` (`src/desk.mjs:588-589`): `const era = v2 ? 2 : Number(f.era || 0) + 1`. A pre-change aggregate therefore keeps minting era 1 (or 2, 3, … from the counter). CHANGE.md: “Swaps created **after this change** persist `era:2`.” Observed: old desk + change `offer-swap` → `era:1`. Those new swaps do **not** `swap_hold` and still complete on `respond-swap accept` (old-instance behavior applied to a post-change swap).

**Finding F10 — pre-change second swap (`era:2` counter) cannot be accepted on the change program.** Class: application defect. Severity: high.

r2/build `offer-swap` sets `era = Number(f.era||0)+1` (`r2/build/src/desk.mjs:546`). First swap era 1; after decline, second swap era 2, still v1 owner.

Scratch:

1. r2/build: open, assign two parties, offer/decline, offer again → `era:2` pending.
2. r2/change `respond-swap sw2 accept` → `{error:"bad_args"}`.
3. Status still pending. Host took the era:2 branch (`src/desk.mjs:640-643`) and issued `accept_swap`, which **does not exist** on v1 (`desk.v1.ik.toml` has no `accept_swap`). `mapKernelError` maps `refused` to `bad_args`.

C4 (“era:1 pending still completes on accept”) is true only for the first swap. The build-stage counter violates CHANGE.md’s assumption that `era:2` means “new program.” Tests (`tests/desk.test.mjs:311-345`) only drive `/tmp/desk-prior-N12r2` through a **first** offer (`assert era === 1`).

## 7. Hollow paths / unused rules

**Finding F1 — r1/build `package.json` is invalid.** Class: application defect (artifact also looks like tool-output contamination). Severity: high (project unusable).

File is 421 bytes. `json.loads` fails with extra data at byte 187. Trailer is the literal sentence “You have received this identical output 3 times. Re-reading '…/package.json:raw' will not change it — use a narrower selector…”. Node 22: `ERR_INVALID_PACKAGE_CONFIG` on `./run open`. `r1/change/project/package.json` is the same object without the trailer (185 bytes) and runs.

**Finding F11 — r1 success no-op only if the last notice is this pair.** Class: application defect. Severity: medium.

BRIEF R5 / assign: after a successful send, repeating that pair is a success no-op without a provider call. r1 (`cmdAssign` `509-525` build / `515-525` change): no-op requires `occupying && notice==="sent" && saved.shift_id/volunteer match`. After a later assign, saved is the other pair → `already_assigned`.

Reproduction (r1/change): assign `s1 v1`, assign `s2 v2`, assign `s1 v1` → `{error:"already_assigned"}`. Tests only repeat the **last** assign (`tests/desk.test.mjs` “noop”). r2 uses `volunteers.includes` and would no-op.

**Finding F12 — completed `accepted` swap permanently `swap_open`s.** Class: application defect. Severity: medium.

CHANGE quiet fact: `swap_open` while pending **or accepted**. After confirm, r1 keeps `swap.status:"accepted"` in JSON; r2 `commit_sms` writes `swap_status:"accepted"`. r1/change `cmdOffer` `573`; r2/change `583`. Scratch (r1/change): after successful confirm, second `offer-swap` → `swap_open`. Pre-change program (r1/build source `563`; r2/build `541`) only blocked `pending`, so a desk that **completed** a swap under the old program cannot offer again after the change. Old-instance regression on an unnamed command.

**Finding F13 — r1 `already_assigned` before send is dead.** Class: application defect (hollow). Severity: low.

Assignments are only appended in `applyCallout` after provider success. Occupying-before-send cannot happen on the writer path, so the `already_assigned` branch is unused except as the misfire in F11.

**Finding F14 — r1/change tests pin era:1 by writing JSON through the current machine.** Class: application defect (test). Severity: low as coverage, not as product.

`tests/desk.test.mjs:249-264` calls `agg.command("offer_swap", {swap_json: era1})` on the change binary. That does not prove a store produced by r1/build (unusable) or `owner` routing.

**Unused / weak machine rules.** r1 `invariants.notice_attempt` only `exists(notice_id)` in `awaiting_effect`. Corpus `desk.ik.cases.json` feeds host-shaped JSON blobs; it cannot witness overlap/`swap_hold`. r2 v2 `accept_swap` / `set_buddy` are used on new desks; they are unreachable on v1 owners (F10). Callback handlers always ignore well-formed JSON (allowed by BRIEF). r2/change README still omits `confirm-swap` from the command list.

Unknown command on r1 is `bad_args` (CHANGE.md’s `unknown_command` describes the **pre-change** program).

## 8. Single edit that keeps the app working while bypassing the runtime

**r1 (change; build source is the same persistence idea):** in `src/desk.mjs`, replace `Kernel` / `agg.command` / `createWith` with read/write of `STATE_DIR/desk.json` holding `{desk_id, shifts, assignments, swap, notice*}`. Every guard (overlap, full, era, hold, buddy) already runs before the command. `begin_notice`/`commit_sent` do not re-check those rules. The process would still POST/GET the gateway.

**r2:** same, using a JSON object with the flat facts already on `agg.state` (`desk_id`, `roster`, `pending_sms`, `swap_*`, `era`, `buddy_id`). `replace_roster` and `commit_sms` already trust host `roster`. Skipping `prepare_sms` + `recordEffectOutcome` and writing `pending_sms`/`notice` in that file is enough to drop Ikaros while keeping HTTP recovery logic.

A still smaller r2 bypass of the **effect** (not the whole store): call `commit_sms` with `notice:"sent"` without `recordEffectOutcome`. `commit_sms` `when = "pending_sms == 1"` does not require a recorded outcome (`machines/desk.ik.toml` v1/v2). The host can mark sent without a matching provider body if it also skips the HTTP mismatch checks.
