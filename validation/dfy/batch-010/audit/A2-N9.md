## Verdict (short)

All four apps commit create/send/sign/decline/archive through the Ikaros client (`create_with` / `execute` / `command`). None keep envelope lifecycle in a JSON sidecar.

They still do **not** treat the runtime as the only authority:

- **r1** never plans a kernel effect. `send` is host GET/POST plus `save_attempt`/`mark_sent` facts. The machine will `mark_sent` with no HTTP.
- **r2** does plan a kernel effect and `record_effect_outcome`, but `mark_sent` / `mark_s1` / `mark_sent_dual` do **not** require a recorded outcome. Skipping `record_acceptance` still reaches `sent`.
- Neither replica calls `lookup_operation`. r1 pins stable `operation_id`s; r2 `command()` generates a new id every call.
- Change-stage **command** routing uses `Aggregate.owner`. r1 still **shows** a v1 aggregate through the v2 machine as a discovery probe (it succeeds). Commanding that v2 handle is `IK_MACHINE_MISMATCH` (observed on r2).
- **C4** (`extend-deadline` on pre-change one-signer envelopes) is refused as `invalid_state` on both change apps. Frozen v1 specs have no extend command; adding one would change `spec_hash`. That is a candidate/guide clash with CHANGE.md, not a missed owner map.

HTTP lost-reply (stub `drop_reply`) is handled: `service_unavailable`, `send:"attempt_saved"`, `reconcile` adopts the same request id, one effect. That path is service lookup, not kernel operation lookup.

### r1/build — runtime facts, no kernel effect

|---|---|---|

| `callback` | may `mark_sent` after GET | GET |
| `status` | `show` | none |

### r1/change — same pattern plus v2 facts

New envelopes: `v2.create_with` (`desk.py:444–446`). Persisted v1 envelopes: `resolve_envelope` (`128–143`) then `apply_named` on the owner handle. Two-signer send loops slots (`555–610`) with request ids `<id>.s1` / `<id>.s2`. `extend-deadline` is v2-only (`666–704`).

### r2/build — kernel effect + two stores

| CLI | Runtime commit | Store |
|---|---|---|
| `create-envelope` | envelope `create_with("open")` then document `create_with("claim")` | two SQLite files |

`record_acceptance` (`desk.py:304–312`) binds the HTTP body digest to `pending_intent`. `finish_sent` (`315–323`) does not check that the effect is recorded.

### r2/change — dual slots on v2; owner load

New 6-arg and 8-arg creates both go through `ENV_V2` (`344`, `396`). `load_envelope` (`132–158`) returns a handle only when `agg.owner == machine.identity`. Dual send: `save_attempt` / `save_attempt_s2` + `mark_s1` / `mark_sent_dual` (`448–583`).

## 2. Duplicate authorities / shadow state

### F1. r1: host HTTP is not a kernel effect; `mark_sent` does not require a service record

**Where:** r1/build `machines/envelope.ik.toml:36–41` (`mark_sent` when `send_status == 'attempt_saved' && exists(request_id)` only); r1/build `desk.py:347–350,353–391`; r1/change `machines/envelope_v2.ik.toml:58–63`, `desk.py:526–537`.

**Cause:** The saved attempt is a fact (`send_status`/`request_id`), not `effect = { kind, id, payload_digest, idempotency_key }`. `commit_sent` / `mark_sent` can run after a fake or skipped POST. The provider request is bound only by host string `request_id == envelope_id` (or `.s1`/`.s2`).

**Repro (kernel, no HTTP):** in scratch, `create_with` + `save_attempt` + `mark_sent` on r1/change v2 reached `state=sent` with no stub. Same class of host-only send as the CLI `cmd_send` after the GET/POST block is deleted.

**Severity:** high (lifecycle `sent` is not coupled to an accepted effect). **Class:** application defect. Guide (`docs/python.md` recording recipe; `skills/ikaros/build.md` step 8) tells builders to plan/record effects; the brief still requires exactly-one service effect, which r1 enforces only in host control flow.

### F2. r2: kernel effect exists, but `mark_sent` ignores it — disposable bypass

**Where:** r2/build `machines/envelope.ik.toml:36–38`; r2/change `machines/envelope_v2.ik.toml:50–71`; r2/change `desk.py:437–469,490–508`.

**Cause:** `save_attempt` plans `signature_request`. `finish_slot` / `finish_sent` then `command("mark_sent"|"mark_s1"|"mark_sent_dual")` with **no** `when` on recorded outcome. Observed in scratch against r2/change v2:

- one-signer: `save_attempt` left `effect.status=pending`; `mark_sent` committed `state=sent` with effect still `pending`.
- dual: `mark_s1` committed `s1_recorded` with effect still `pending`.

**Disposable shadow-state check:** one edit — make `record_acceptance` return `agg` unchanged (skip `record_effect_outcome`). `deliver_current` still POSTs (or not) and `finish_slot` still marks `sent`. CLI tests that only assert `state`/`send` keep passing; the runtime effect is unused for the transition.

**Severity:** high. **Class:** application defect (machine under-constrained). Not a guide defect: `docs/python.md` already requires record-then-finish.

### F3. r2/change: `extend-deadline` during `attempting` POSTs a different payload than the planned digest

**Where:** r2/change `desk.py:490–508,511–524,673–704`; `machines/envelope_v2.ik.toml:96–101` (`extend_attempting`).

**Cause:** `save_s1` hashes the payload at save time (`payload_digest`). Public `attempting` is still `draft` (`169–172`), so C4 extend is offered. Extend updates `deadline_ms` / `expiry_ms` and does **not** re-plan the pending effect. Later `send` POSTs the new deadline under the same `request_id`.

**Repro (observed):**

```text
create-envelope envE docE s1 a@b.c 100 10
CRASH_AT=after-attempt-saved-before-request send envE   # send=attempt_saved, deadline 100
extend-deadline envE 200 20
send envE   # success, state=sent
```

Stub `/effects` stored `deadline_ms: 200`. Planned intent still had the digest of deadline 100. Kernel accepted `record_effect_outcome` because it never sees the HTTP body.

**Severity:** medium (same request id, different payload than the committed plan; lucky here because no POST had occurred yet; after a POST of the old body this is 409). **Class:** application defect.

### F4. r1/change host `send_s1`/`send_s2` facts duplicate “both accepted”

**Where:** r1/change `desk.py:503–537,573–608`; v2 `mark_s1`/`mark_s2`/`mark_sent` when-guards.

**Cause:** Host `slot_done` / `both_complete` decide whether to `mark_sent`. The machine repeats the same predicate. Not a second file, but a second decider. Diverges if host `commit_sent` is skipped while facts say both sent (or the reverse).

**Severity:** low. **Class:** application defect.

## 3. Partial-commit seams

### F5. r1 create: envelope commit then best-effort id claims (errors swallowed)

**Where:** r1/build `desk.py:307–327`; r1/change `desk.py:344–350,456–466`.

**Cause:** `create_with` on the envelope is one kernel transaction. `claim_m.create(id)` is a later genesis, and `except KernelError: pass`. Crash or a swallowed claim failure leaves an envelope whose `document_id` is not reserved. Next `create-envelope` with that document id: `id_taken` looks up the document as an envelope or claim; both miss; R6 can fail.

**Repro:** SIGKILL between `create_with` return and `claim_id` (no `CRASH_AT` on create; needs an injected kill). Code-causal; not exercised with the shipped crash labels.

**Severity:** medium. **Class:** application defect.

### F6. r2 create: envelope store then document store (two files, two commits)

**Where:** r2/build `desk.py:83–88,267–291`; r2/change `desk.py:88–93,318–327,344–365,396–420`.

**Cause:** `envelopes.sqlite` commit is durable before `documents.sqlite` `claim`. Crash between them: envelope exists, document slot free. `id_taken(document_id)` is false. A second envelope can reuse the document id (R6). The reverse (claim without envelope) is `id_in_use` on a later retry of the same create (`HistoricalResult` on claim) **after** a duplicate envelope already exists.

**Severity:** medium. **Class:** application defect. Topology note: Ikaros cannot atomically span two stores (`skills/ikaros/build.md` step 2). Using two stores for one admission is an application choice (r1 used one store).

### F7. r1/r2 send: POST accepted, then crash before `mark_sent` / `record`

This is the specified `after-accept-before-record` seam. Both honor it (r1 `desk.py:388–390`; r2/build `377`; r2/change `505–508`). Local `send:"attempt_saved"`, service has the effect; retry GET 200; no second effect. **Not a defect** relative to R8. r1 does that without a kernel pending intent (F1); r2 has a pending intent but may skip recording (F2).

## 4. Operation / effect binding

### F8. No `lookup_operation` in any replica; r2 issues a new kernel operation id per `command()`

**Where:** no `lookup_operation` in any `desk.py`. r1 `apply_named` (`desk.py:137`) passes a stable id (`save-attempt:<id>`, `mark-sent:<id>`, `sign:<id>:<now>`). r2 `agg.command(...)` (r2/build `desk.py:351–356,395`; r2/change `516–521,611`) uses `Aggregate.command`, which generates a fresh id (`invariant_kernel/client.py:471–476`). `record_effect_outcome` is also called without `operation_id=` (r2/build:310; r2/change:443).

**Cause:** A lost kernel reply on r1 retry of the same CLI args is an exact repeat (historical) or a fresh execute under the original capability path after `show`. On r2, a lost `sign`/`mark_sent` reply is `TransportError` → `service_unavailable`; the retry is a **different** operation id with a refreshed handle. If the first commit landed, the user sees `invalid_state` rather than success. `docs/client-recovery.md` / `docs/python.md`: reconcile with `lookup_operation`; do not mint a new id.

**Provider request:** r1/r2 `send` always GET then POST-on-404, using the saved request id. A second POST for the same attempt happens only on GET 404. Observed `drop_reply`: one stored effect, reconcile does not POST again.

**Severity:** medium (kernel recovery); provider binding for `send` is OK at the HTTP id layer. **Class:** application defect (guide is explicit).

### F9. r1/change two-signer: `reconcile` reports `not_sent` after a 200 lookup of s1

**Where:** r1/change `desk.py:707–761`.

**Cause:** After `after-accept-before-record` on signer 1, only `envT.s1` is stored. Reconcile marks s1, then GET s2 → 404, sets `missing=True`, returns `send:"not_sent"` even though s1 was 200. Status still `attempt_saved`. R11: do not report `not_sent` after a 200 lookup. C5: recovery must not invent a second id (this path does not), but it **does** lie about lookup.

**Repro (observed):**

```text
create-envelope envT docT sA a@b.c sB b@c.d 100 10
CRASH_AT=after-accept-before-record send envT
reconcile envT   # {"send":"not_sent", "request_id":"envT.s1", ...}
# /effects count=1 (envT.s1 only)
status envT      # send=attempt_saved
```

**Severity:** medium. **Class:** application defect.

r2/change after the same crash: `reconcile` stays `attempt_saved` (does not POST s2; `drive_send` `allow_post=False` returns at `s1_recorded`, `desk.py:563–567`). Subsequent `send` completed both ids, two effects. Compatible with “reconcile never POST” (R11) plus C5’s “reconcile **or** send”.

## 5. Error / unknown outcomes

### F10. Uncertain kernel transport is mapped to `service_unavailable` without lookup

**Where:** r1 `apply_named` `desk.py:138–144` (`classify` not `not_found`/`refused` → `fail("service_unavailable")`, including `uncertain`); r1/change `main` `874–875`; r2 `main` `TransportError` → `service_unavailable` (r2/build `554–555`; r2/change `792–793`).

**Cause:** A timeout after dispatch is `submission-unknown` (`docs/client-recovery.md`). The apps treat it as a domain service failure. For `send`, retry via GET is still safe. For `sign`, it can hide a committed decision (F8).

HTTP 5xx / drop / connect failure: observed `drop_reply` → `service_unavailable`, attempt retained, reconcile by GET. **That** unknown path is correct for the brief.

**Severity:** medium. **Class:** application defect.

### F11. Host pre-filters map kernel expiry to `expired`; without them the kernel is `invalid_state` / invariant

**Where:** r1/build `cmd_sign` `402–410` then `apply_named` maps all `refused` → `invalid_state` (`142–143`). Scratch: v2 `sign` with `now_ms=101` after `mark_sent` raised `IK_INVARIANT_FAILED`, classified `refused`. r2 host `now_ms > expiry_of` (r2/change:609) before `command("sign")`.

**Cause:** Distinct brief codes (`expired` vs `invalid_state` vs `not_sent`) cannot come from the kernel alone, so the host decides the same transitions the machine guards. If host and `when` diverge (F3 deadline vs `decision_until_ms` / `expiry_ms`), the user-visible code is the host’s.

**Severity:** low as mapping; it is why the host is a second authority (section 2). **Class:** application (error-code mapping). Guide (`build.md` step 8) wants translation of **runtime** refusals by class, not a parallel host state machine.

### F12. r2 `main` does not catch generic `KernelError` (R12)

**Where:** r2/build `desk.py:546–557`; r2/change `784–795`. Catches `AppError`, `IllegalStateError`, (`CommandInvalidError` in change), `TransportError`. Not `EffectConflictError`, `OperationConflictError`, `MachineError`.

**Cause:** An effect-digest conflict or a mistaken v2 command on a v1 handle (`IK_MACHINE_MISMATCH`, observed below) can traceback with no JSON object. r1 maps all `KernelError` to `service_unavailable`.

**Severity:** low (happy-path unhit). **Class:** application defect vs R12.

## 6. Persisted owner routing (change stage)

### What works

Both change apps keep `envelope.ik.toml` v1 byte-for-byte with build (same `machine_id` / version 1). New instances are created on v2.

**r1/change** `resolve_envelope` (`desk.py:128–143`): `show` v2 then v1; `by_owner[shown.owner]`; re-`show` on that machine. Commands use the routed handle.

**r2/change** `load_envelope` (`132–158`): iterate v2 then v1; return only if `agg.owner == machine.identity`.

**Observed continuity (scratch):**

| Step | r1/change | r2/change |
|---|---|---|
| build `create-envelope env1 ... 100 10` | draft v1 | draft v1 |
| change `status env1` | draft, deadline 100 | draft, deadline 100 |
| change `extend-deadline env1 200 20` | **`invalid_state`** | **`invalid_state`** |
| change `send env1` | sent, `request_id=env1` (not `.s1`) | sent, `request_id=env1` |
| change `sign env1 50` | signed | signed |

New post-change one-signer (`envN` on r2): extend to 200 then sign at 150 succeeded (v2 `expiry_ms=deadline`).

### F13. Discovery `show` of a v1 aggregate through the v2 machine succeeds; commanding it does not

**Where:** r1/change `desk.py:129` (`try_show(v2, envelope_id)` first); r2/change loop still **calls** `v2.show` (`140–143`) then rejects on owner mismatch.

**Observed (r2/change, env1 created by build):**

```text
v2.show env1  -> state signed, owner MachineIdentity('envelope_desk', version=1)
v2.command("sign") / extend_sent -> MachineError IK_MACHINE_MISMATCH contract_mismatch
v1.show env1  -> same facts, owner v1
```

r1/change probe: `v2.show('env1')` also succeeded with `owner version=1`; they then re-show v1. They do **not** command the v2 handle (the `if machine is v2 or machine is v1` re-show). Residual: any future use of the first `shown` handle would be F12/mismatch.

**Severity:** low (commands are owner-routed). **Class:** application caution, not a continuity break.

### F14. C4 extend on pre-change (v1) envelopes is impossible without breaking identity

**Where:** r1/change `desk.py:684–685` (`if agg.owner.version == 1: fail("invalid_state")`); r2/change `673–696` issues `extend_draft` etc. that **do not exist** on v1 (`CommandInvalidError` → `invalid_state`). v1 tomls have no extend command (r1 `machines/envelope.ik.toml` 61 lines, identical to build).

**Cause:** CHANGE.md C4: “Existing one-signer envelopes may use it, but their original expiry rule remains in force.” Ikaros change (`skills/ikaros/change.md` 5a): do not rewrite stored identity; do not add commands to the frozen v1 spec (new `spec_hash` → `IK_MACHINE_HASH_MISMATCH`). Commanding v2 against a v1 owner is `IK_MACHINE_MISMATCH` (F13). There is no legal runtime write of `deadline_ms` on a v1 instance except commands v1 already had.

**Severity:** high vs C4 text; **correct vs Ikaros owner freeze**. **Class:** candidate/guide defect (CHANGE.md vs frozen owner). Applications honestly refuse rather than host-write a shadow deadline.

## 7. Hollow paths / unused rules / tests

### F15. r2 CLI success bodies ignore the committed state

**Where:** r2/build `cmd_sign` `395–398`, `cmd_decline` `413–415`; r2/change `611–613`, `628–630`, `641–643`. `settle(result)` is discarded; JSON `state` is a string literal.

**Cause:** If `command` returned historical or a surprising state, the CLI still prints `signed`/`declined`/`archived`. Host already refused illegal states, so tests stay green.

**Severity:** low. **Class:** application defect.

### F16. Hollow / weak tests around the risky recoveries

**Where:** r1/change `tests/test_desk.py:309–312` (`if body["send"] != "sent": send` after reconcile — C5 is not required of reconcile). r2/change `tests/test_desk.py:214` (`effects_count(ctl) == before + 1 or effects_count(ctl) >= before` — the `>= before` arm is almost always true). Neither change suite creates a **build-app** envelope and then extends it (F14 untested).

**Severity:** low (tests exist and do run process crash/lost-reply for one-signer). **Class:** application defect.

### Unused machine surface

- r1 `id_claim.ik.toml` command `touch` is never called (`desk.py` only `create`).
- r2 v1/v2 `mark_sent*` have no recorded-effect guard (F2) — the planned effect is unused for the transition.
- r1 host `expired`/`not_sent` checks mean the corresponding `when` clauses are not what produces the brief error code (F11).

## 8. Disposable shadow-state check (summary)

| App | Single edit that keeps the CLI working while bypassing the runtime’s real rule |
|---|---|
| r1 | Delete the GET/POST in `cmd_send` and keep `save_attempt` + `mark_sent`. Machine allows `sent` with only a `request_id` fact (F1). |
| r2 | Make `record_acceptance` a no-op. `mark_sent` still commits `sent` with `effect.status=pending` (F2). |

That is the tell: the kernel is used as a durable log of host decisions, not as the gate on “accepted signature_request”.
