## Verdict (short)

No host JSON/usage/cache file is a second **writer**. Lifecycle commits go through Ikaros (`createWith` / `command` / `execute`, `recordEffectOutcome`). Both change replicas route persisted aggregates with `aggregate.owner` (r2 via `identity.equals`; r1 commands via `identity.equals`, edition label via `owner.version`).

The serious defects are **host views that disagree with the runtime store after `promote`**, and **deadline/amount formulas that live in the host, not the machine** (fatal for r2 old-instance policy). r1/change `promote` does not clear deposit facts; `status`/`promote` JSON null them; `reconcile` of the leftover id returns `corrupt_state`. Original-instance tests are not in-repo: they point at shared `/tmp` stores that the tests themselves expire.

### F2. r1/change: leftover `deposit_id` is still reconcile authority → `corrupt_state` (high, application)

`cmdReconcile` (`src/cli.mjs:601`) treats any `facts.deposit_id` as a saved attempt. After F1, `reconcile L1 <old id>`:

1. not `no_deposit` (string still set)
2. GET 200 of the prior hold (`outcome:"held"` still on the stub object)
3. `matchingHeld` succeeds (leftover `deposit_offer_id`/`deposit_buyer_id` still O1/B1)

Observed: `{"error":"corrupt_state"}`. Spec after promote: no saved deposit (`no_deposit`), no mutation. Status still showed `offered` / `edition:"revised"` after that refuse.

Causal: host JSON and `depositFieldsForStatus` are not the store; `reconcile` reads the store.

### F3. r2/change: leftover `deposit_id` string after promote (medium, application)

`listing_v2.ik.toml:108-113` zeros `accepted_ms`, `deposit_deadline_ms`, `deposit_cents`, `has_deposit`, `has_backup`. It does not clear the `deposit_id` string (or `backup_offer_id`).

Scratch `/tmp/InspectN15-scratch/r2c-promote` after promote: `has_deposit: 0`, `deposit_cents: 0`, `accepted_ms: 0`, `deposit_deadline_ms: 0`, **`deposit_id` still `d705d035c8d6526265098d3f4`**.

`liveDepositId` (`desk.mjs:169-175`) and `cmdReconcile` (`:606`) key off `has_deposit`, so `status` hides the id and `reconcile` correctly returns `no_deposit`. Shadow fact, not a writer — but a store-sufficiency test would fail “clears deposit fields”, and a later host that reads `deposit_id` alone would revive F2.

### F4. Deposit deadline and `deposit_cents` formulas are host-only except r1 v1 (high for r2 old instances, medium otherwise)

- r1 v1 machine: `$deposit_deadline_ms == accept_by_ms` (`desk.ik.toml:91`). Original listings cannot be given a revised deadline by a mistaken host arg.
- r1 v2: `$deposit_deadline_ms >= $now_ms` (`desk_v2.ik.toml:92`). Formula `accepted_ms + deposit_window_ms` is only `depositDeadline()` at `cli.mjs:322-326`.
- r2 v1 and v2 `accept` store whatever `$deposit_deadline_ms` the host sends (`listing.ik.toml:72`, `listing_v2.ik.toml` accept outcomes). C4 original deadline is a host `if` at `desk.mjs:491-495`, not a machine law.

`deposit_cents = floor(n/50)` is host-only in all four (`cli.mjs`/`desk.mjs` lines above). Machines accept `$deposit_cents >= 0`.

## 3. Partial-commit seams

Labeled `CRASH_AT` points match the brief: save attempt, then POST; after HTTP success, before fund record; after fund record, before stdout.

Unlabeled gaps (all four, medium, recovered by GET + same id):

1. `recordEffectOutcome` then `complete_hold`/`fund` — crash between them leaves `attempt_saved` + one provider hold; later `deposit`/`reconcile` GET-adopts without a second POST (r1 `recordAndCompleteHold`, r2 `commitFund`).
2. Fallthrough: `plan_release`/`start_release`, POST, record, `complete_release`/`mark_fallen`. No `CRASH_AT`. Retry re-POSTs the same id (provider release is idempotent) if `pendingIntent` is still the release; if record succeeded and complete did not, a second `plan_release` is possible. Spec does not name a release crash label.

r2 `deposit_gate` (`desk.mjs:494` build / `:540` change) is an extra no-op commit on every unfunded `deposit` **before** save/POST. Crash between gate and `save_deposit` is retry-safe. Past-deadline `deposit` on `attempt_saved` expires without lookup (same in r1, which checks deadline before GET). Brief command text prefers `deposit_elapsed`; R9 says “later deposit adopts”. Ambiguous; not filed as a defect.

## 4. Operation / effect binding

What holds: first deposit allocates one id, commits it (`plan_deposit` / `save_deposit` effect id = deposit id), then POSTs that body. Repeat `deposit` with `attempt_saved` GETs first; POST only on 404 with the **same** id. Funded path is a no-op (r1 `deposit_funded_noop`, r2 host short-circuit). Release uses `r-{deposit_id}` / `r`+id as idempotency key.

### F5. No `lookupOperation` (low vs BRIEF HTTP recovery; medium vs Ikaros record recovery)

None of the four call `Machine.lookupOperation`. Lost CLI after a kernel commit is recovered by domain idempotency (`already_open`, `already_offered`, funded no-op, GET adopt). Lost `recordEffectOutcome` is retried by walking HTTP again, not by looking up the kernel operation id. `docs/client-recovery.md` / `docs/typescript.md` want lookup for `submission-unknown`. Brief recovery is the escrow GET.

A second POST for the same attempt is possible after GET 404 (required by the brief).

## 5. Unknown outcomes

Transport / empty body / non-JSON / HTTP 5xx → `service_unavailable`, leave `attempt_saved` / under-contract. Matching 200 is required before fund. Mismatching 200 → `lookup_conflict` (no POST of a new id). Dropped reply: incomplete or socket error → unavailable, later GET adopts.

r1/change `httpJson` (`cli.mjs:257+`) returns `kind:"ok"` for 5xx; callers still map `status >= 500` or the final `fail("service_unavailable")`. r1/build classifies 5xx as `unavailable` at the HTTP layer.

### F6. r2 kernel refusals mapped to the wrong domain code (low, application)

`cmdBid` catch → `desk_full` (`desk.mjs:395` build, same pattern in change). `cmdPromote` catch → `no_backup` (`desk.mjs:715` change). A machine mismatch or unexpected refuse becomes a named domain error without mutation.

## 8. Disposable shadow-state check (the single edit)

There is no sidecar to delete. The edit that keeps `./run` green while the runtime store diverges:

**r1/change:** `depositFieldsForStatus` (`cli.mjs:131-134`) and `cmdPromote`’s literal nulls (`:704`) already substitute CLI amounts for runtime facts. Changing only those host views (or `depositDeadline` at `:322-326` for revised listings) does not require a machine edit; v2 `accept` will store any `deposit_deadline_ms >= now`.

**r2/change:** change `desk.mjs:492-495` to always `now + deposit_window_ms`. v1 `accept` will persist it. C4 dies; `status`/`deposit` still go through Ikaros.

**All four:** change `Math.floor(amount/50)` to another constant; machines still commit `deposit_cents`.

Bypassing the kernel entirely (commenting out `command`/`execute`) would break durability unless a new file were introduced; they did not introduce one.
