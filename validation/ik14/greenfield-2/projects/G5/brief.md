# Building inspection scheduler

Implement `./run` as a one-command-per-process local application using `STATE_DIR` and `SERVICE_URL`. For every ordinary command, stdout is exactly one JSON object and contains no other text; success exits 0 and refusal exits nonzero with `{"error":"<message>"}`. An intentional `CRASH_AT` termination does not exit 0 (the test treats either a nonzero exit or signal termination as failure) and may produce no JSON. Diagnostics may go to stderr. No wall clock. Concurrent local processes and process restart are in scope; distributed coordination is not.

Commands: `schedule <plan_id> <site_id> <inspection_type> <count>` creates a finite schedule; `status <plan_id>`; `advance <plan_id>` performs the next inspection; `cancel <plan_id>`. Identifiers match `^[A-Za-z0-9_-]{1,64}$`; count is integer 1..4. One stable task id per occurrence is `<plan_id>:<1-based-index>`. Service POST is idempotent by task id; lookup returns task outcome. Service may apply then lose its reply.

Each success prints the schedule record as the root JSON object, not nested under another key. Its fields are `plan_id`, `site_id`, `inspection_type` (the original strings), `phase`, `next_index` (1-based next occurrence, or `count+1` after all complete), `count` (integer 1..4), `completed` (ordered array of task-id strings), and `current_task_id` (the in-flight task id or null when none). Initial phase is `ready`; the initial completed list is empty and current_task_id is null. Initial phase values are `ready`, `uncertain`, `complete`, and `cancelled`.

R1. Schedule validates and persists without service calls; same-store restart observes identical schedule. Duplicate id refuses without mutation.
R2. Invalid inputs, missing environment, unknown command, and unknown plan refuse with JSON errors and make no service calls.
R3. Each advance dispatches only the next task id; confirmed outcome appends it once, increments next_index once, and reports complete after the final task. Repeated advance cannot duplicate a completed task.
R4. If the service applies a POST but its reply is lost, the command may exit nonzero; the record becomes `uncertain`, retains the same `current_task_id`, and does not advance `next_index` or append that task to `completed`. Recovery MUST GET that task id before any resend. When lookup returns `confirmed`, recovery MUST NOT POST it again. The required lost-reply case uses task id `pu:1`: the service records the POST, closes the connection without an HTTP response, then returns the recorded `confirmed` result on lookup. At most one external inspection is performed per occurrence.
R5. `CRASH_AT=after_schedule` terminates without exit code 0 after the schedule commit and before any request. Restart sees phase `ready`, index 1, and can progress.
R6. `CRASH_AT=after_send` terminates without exit code 0 after the service records the task and before local result commit. Restart sees `uncertain`; recovery looks up and reconciles the same task, succeeds with exit 0, does not POST again when lookup returns `confirmed`, preserves one effect, then continues at the next index.
R7. Cancellation is durable and idempotent. In the required `pc` cancellation race, count is 3; `pc:1` is already completed, and the service applies `pc:2` but withholds its successful response until `cancel pc` returns. Cancel MUST exit 0 with phase `cancelled` before that response is released. After release, the in-flight `advance` may exit 0 or nonzero; its exit status does not determine acceptance, but it MUST terminate. Status MUST be `cancelled` with only the pre-cancel completed occurrence `pc:1`; a late response MUST NOT change that record. A later `advance pc` MUST return the cancelled record without another POST. Cancellation cannot undo external work already performed.
R8. Independent plans progress without clobbering each other; legitimate schedules are not refused; status is local-store-only and does not wait for a service call.
