# Public fake inspection service

The host sets `SERVICE_URL` to the service base URL. The service exposes `POST /tasks` and `GET /tasks/<URL-encoded task_id>` only. A valid POST request body is `{ "task_id": "<non-empty string>", "site_id": "<site id>", "inspection_type": "<type>" }`. For a non-empty string `task_id`, POST records the task idempotently and returns HTTP 200 with `{ "task_id": "<same id>", "outcome": "confirmed" }`. A POST with malformed JSON returns HTTP 400 with `{ "error": "invalid JSON" }`; a valid JSON POST with missing, empty, or non-string `task_id` returns HTTP 400 with `{ "error": "task_id required" }`.

GET decodes the URL-encoded task id. If recorded, it returns HTTP 200 with `{ "task_id": "<same id>", "outcome": "confirmed" }`; if not recorded, it returns HTTP 404 with `{ "error": "not found" }`. Any unsupported method or route returns HTTP 404 with `{ "error": "not found" }`. All responses have `content-type: application/json`. Clients MUST look up an uncertain task before retrying its POST.

The test scenarios use the same successful and error response shapes. Fault behavior is supplied by the test environment, not by public routes or client settings: the `pu:1` lost-reply case records the POST then closes the connection without an HTTP status or body; a subsequent GET returns the recorded 200 response. In the `pc:2` cancellation race and the `pp:1` pause race, the POST is recorded idempotently and its normal HTTP 200 response is held until the specified cancel or pause command returns; the released response has the confirmed body above. No other wire shapes occur in these scenarios.
