# BUILD

Entry: a behavior request, a project you can read, and no presumed solution. Mode in `skills/desmo/routing.json` is `build` once you are writing. Until then stay on `read` and `scratch`.

## Steps

1. Inspect authorities, writers, transports, and deployment. The installed-surface read is Discover step 1 in `skills/desmo/SKILL.md` (`desmo` is `npx --no-install desmo`; a Python project has none). A missing store on a read is not corruption. The read does not create one.
2. Decide fit. First try to put the facts that must change together into ONE aggregate (one machine, one store). If Desmo would still split a transaction the product must keep atomic, stop. Cite the requirement and the topology conflict, and name the simpler path. Do not force adoption. Never close the gap with a host saga across two stores, a sidecar file, or a host branch that decides lifecycle: that makes the host a second authority and a crash between the steps leaves them disagreeing. When no human can answer, deliver only what one aggregate can honor and list the unmet requirement in the handoff.
3. Derive the behavior contract: outcomes, unchanged obligations, effect boundary, unknowns. Resolve anything the repo or a scratch fixture can answer. Ask the human only with the decision template in `skills/desmo/SKILL.md`.
4. Freeze acceptance cases from that contract before you treat a green run as success. A scenario that always refuses does not pass.
5. If there is no machine yet, `desmo init --template job --language typescript [--out <dir>]` writes a job project, `.ik/checks.toml`, `scenarios/normal.json`, `scenarios/stale-handle.json`, and `job.ik.cases.json`. Exit 0 means those files were written. It does not mean a command can commit.
6. `ik identity <machine.ik.toml>` is the machine identity. `ik laws <machine.ik.toml>` is advisory. `ik schema <machine.ik.toml>` feeds generation.
7. `desmo codegen <machine.ik.toml> [--out <file>] [--check] [--import-from <specifier>]` writes a disposable TypeScript projection. `--check` exit 1 means the file is stale or missing. Types are not ownership: a copied handle is still refused at runtime.
8. Author the machine and route every named writer, including workers, callbacks, and recovery, through the domain API. No host status branch may decide the same lifecycle. Any amount, deadline, approval predicate, or invalidation the contract names MUST be enforced by a guard (the host may compute and propose the value; the guard checks the relationship). A host-only check is bypassable through the command interface. A command that clears or invalidates state must clear every fact the next reconcile or projection reads. A reconcile on a terminal state must not require a live provider.
   - Input validity is a business rule too. If the contract says a command's input must be non-empty, bounded, in a set, or related to a fact (for example a required reviewer id or a note that must not be blank), write it as a `when` guard on that command, with a corpus case for the refusal. A check only in the domain API or host wrapper is bypassable through the command interface, the same as an amount or deadline.
   - After authoring, run `ik laws <machine.ik.toml>` and read `unguarded_arguments`: each entry is a declared argument that no `when` reads. It directs attention; it does not prove protection. Resolve each entry against the contract, and prove the result by sending a violating request directly through the runtime with valid authority and seeing it refused with state unchanged. A rule stated through a shared type, such as an identifier grammar ("1 to 64 characters of A-Za-z0-9._-"), binds every argument of that type and is encoded as `text_in($arg, 'A-Za-z0-9._-', 1, 64)`. Dispositions for the handoff: (a) the contract constrains its value or its relation to state: name the authoritative enforcement (a guard, or an invariant that constrains the resulting state) and the direct runtime refusal you exercised; (b) opaque data with no contractual constraint beyond its type: say that no additional constraint is required, and do not add a meaningless guard to clear the entry; (c) it carries an external assertion such as an authenticated identity or an observed time: name the trusted source and the runtime checks that apply, and do not claim that checking the string authenticates its origin; (d) a rule the contract names is enforced only in host code: that is an unmet lifecycle-enforcement requirement, not an assumption and not a documentation item. Do not hand the classification to the requester.
   - A length-bounded character-set grammar is a `when` guard: `text_in($arg, 'A-Za-z0-9._-', 1, 64)` for an identifier of 1 to 64 characters of A-Za-z0-9._-. Write it on every argument that carries that type. An opaque label the contract does not constrain stays unguarded; do not add a meaningless guard to clear the inventory. Residual unmet requirements are only for grammars that are not length-bounded character sets (a checksum, a regex with backreferences, Unicode normalization). A host-only check of an expressible identifier grammar is still bypassable through the command interface.
   - Translate runtime errors into your domain refusals by error class or `error.code`, never by message text: TypeScript `StoreNotFoundError` or `classify()`, Python `StoreNotFoundError`, Go `*StoreNotFoundError`. When each entity has its own store, a missing store on a read of a named entity is your "unknown entity" refusal. A raw `IK_STORE_NOT_FOUND` or other `IK_*` code must never reach your callers as the application's error. See `docs/design/error-taxonomy.md` and `docs/client-recovery.md`.
9. `ik check <machine.ik.toml> --profile <checks.toml> --plan` prints goals, digests, limits, and corpus digest. It does not explore. Exit 0 is not a witness and not a release pass.
10. `ik check <machine.ik.toml> --profile <checks.toml> [--corpus <cases.json>] [--baseline <json>] [--json]` exit 0 means the developer check accepted and every required profile goal was satisfied in this search. `witness_found` is a path the explorer executed. It does not prove unreachability when the search was incomplete or a case was missing. It does not authorize a production commit. Add `--release` only when you need the strict release policy; exit 0 then still does not publish. Without `--corpus`, a refusal is missing evidence, not automatically a machine defect. See `docs/ik-check.md`.
   - The starter from `ik corpus init` is type-valid placeholders and usually witnesses no outcome, so a refusal can persist after you add it. Edit it into witness cases: walk the happy path with arguments that satisfy each command's `when` guard and agree with the facts the earlier command wrote, then add one case per refusal you expect. Rerun, read `NEXT COMMAND` and the uncovered obligations, and report the verdict you reached. A refusal that names uncovered obligations is a gap to list in the handoff, not a pass. Worked corpora: `examples/publish-approval/machines/*.cases.json`.
11. `ik scenario run <machine.ik.toml> <scenario.json> --out <dir>` exit 0 means every expectation was met on a fresh scratch store at `<dir>/scratch/store.sqlite`. There is no `--store` flag. A refused step committed nothing. This does not mean an external executor ran, mail was sent, or an unsubmitted input was proved. Example schedule: `examples/publish-approval/scenarios/adverse-ordering.json`. See `docs/scenarios.md`.
12. `ik scenario reproduce <bundle-dir> --out <dir>` prints `reproduced` when a second scratch run matches the bundle aside from runtime identity. It does not rewrite expectations.
13. `ik report <path> [--json] [--html <file>]` folds scenario, analysis, and profile findings. A model finding stays model-level until `reproduction_status` is `concrete_reproduced`. `unreadable` is not a skip. See `docs/workbench-report.md`.
14. `desmo trace <bundle.json> --out <file.html>` renders advisory HTML. It is not authority and not a commit.
15. Optional specialist, only if the question needs it. `ik analysis describe <manifest.json>` reads a manifest and does not spawn. `ik analysis run <manifest.json> --request <request.json> --out <dir> [--timeout-seconds <seconds>]` is the command that spawns, and only against scratch. Never pass a production store. Exit 0 means the host accepted a result document, not that a property passed, and not that the runtime should commit. `ik analysis validate-result <request.json> <result.json>` rechecks stored bytes and does not spawn. `ik analysis conformance <manifest.json> [--fixtures <dir>]` runs the starter battery through that same host path. Passing it proves the host contract, not engine correctness. See `docs/analysis-adapters.md`. `ik graph export <machine.ik.toml> [--corpus <cases.json>] [--max-nodes <n>] [--max-depth <d>] --out <graph.json>` is a finite graph from the existing explorer. A depth or node cut is incomplete. It is not a proof of the executable runtime. A missing optional engine does not block steps 10 or 11. See `docs/analysis-adapters.md`.
16. Exercise the delivered public interface: one useful path and one meaningful refusal, against real Desmo APIs. Then fill the handoff in `skills/desmo/SKILL.md`. Cite the scenario `result.json` and the check document. List what was not run. `ik handoff <behavior.json> --evidence <path>... [--kind delivery|change|recovery] [--json]` renders the handoff from that evidence. The first line is `Desmo delivery: <subject>`; cited ids sit under `Exact evidence`. Every guarded rule needs `rule_witnesses`: examples (arguments, facts, stated outcome) that tell the rule from its one-step variants, such as a flipped comparison or a boundary moved by one. The handoff checks them and refuses when they are missing or inadequate; the human then accepts each rule, recorded as `accepted_rules` entries with the guard hash and examples hash the handoff prints. The examples test the guard in isolation; they do not show the rule matches the business intent. These checks cover declarative machines only. A facts strip and two-column river map sit in the first block (which ends on the action/decision line); the command table follows. They compress the same evidence, they do not add facts. Mermaid is `ik diagram --format mermaid` only. A claim is `exercised` only when its cited finding ids resolve to statuses that support that item's `claim` (`reconciled` may use `committed_exact` or `historical`; those statuses do not support `new_mutation` or `current_handle`). Uncited, missing, partial, or contradicted claims say so. See `docs/workbench-report.md`.

Criterion origins: for each decision point of each guarded rule, record where it came from in the behavior file: `requirement` `{text, source, provenance}` copied from what the owner gave you (`agent-restated` if you paraphrased it; the handoff says `author-stated, not verified` either way), then an `origins` entry per point: `stated` with a verbatim `span` (add `equivalent` for a value stated in other units), `chosen` when you picked it and the requirement does not say, or `default` with `default_id`. Point keys and the guard hash are in the handoff JSON (`origins.rules[].points[]`). Do not mark a point `stated` unless the requirement names it; a chosen point is not a failure, an unrecorded one reads as a gap. After the owner acknowledges a chosen point, add it to `acknowledged_origins`. See `docs/workbench-report.md`.

What is missing: the handoff lists definition gaps, commands with no cited committed run or guard refusal observed against this definition, and, if you give the requirement as `atoms`, statements nothing implements. Split the requirement into verbatim `atoms` `{id, span}` covering every word of every sentence (a fragment does not cover its sentence; each span must occur once), trace each with `traces` `{atom, element}` (`command:NAME`, `state:NAME`, `fact:NAME`, `invariant:NAME`, `point:RULE/KEY`) or mark it `not_applicable` with a reason. Do not drop an awkward sentence: an uncovered sentence is listed. Do not close a gap by editing the list; close it by fixing the definition, citing the run, or tracing the statement honestly. See `docs/workbench-report.md`.

Client lookup, if a reply is lost during the exercise: TypeScript `Machine.lookupOperation`, Python `Machine.lookup_operation`, Go `Machine.LookupOperation`. See `docs/typescript.md`, `docs/python.md`, `docs/go.md`, and `docs/client-recovery.md`.
