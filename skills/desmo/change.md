# CHANGE

Entry: an accepted machine and a new behavior request. Mode in `skills/desmo/routing.json` is `change` once you edit. Reconstruct before you edit.

## Steps

1. Read the installed surface (Discover step 1 in `skills/desmo/SKILL.md`; `desmo` is `npx --no-install desmo`, and a Python project has none) and `ik identity <machine.ik.toml>` to reconstruct the current identity. Separate old requirements from old implementation accidents. A current `show` is not the history of a past request.
2. State the delta and the unchanged obligations. Ask only when intent changes ambiguously or exceeds delegated authority, using the one decision template in `skills/desmo/SKILL.md`.
3. `ik profile diff <old.toml> <new.toml> [--json]` compares two version-1 profiles. Exit 0 means the diff printed, including a weakened diff. Check `weakened` yourself: a deleted required goal, `required` flipped to false, a smaller search bound, or a new `allow_waiting` state. A goal id is not the requirement. This does not move aggregates and does not change `spec_hash`. See `docs/change-evidence.md`.
4. Derive expected outcomes before editing. Changing a machine is not permission to weaken the user requirement.
5. Change the smallest machine and integration surface. Any amount, deadline, approval predicate, or invalidation the contract names MUST be enforced by a guard (the host may compute and propose the value; the guard checks the relationship). A host-only check is bypassable through the command interface. A command that clears or invalidates state must clear every fact the next reconcile or projection reads. A reconcile on a terminal state must not require a live provider. `desmo codegen <machine.ik.toml> [--out <file>] [--check] [--import-from <specifier>]` regenerates disposable bindings. Keep definitions persisted instances still need. Do not rewrite spec hashes in stored state. Do not invent a generic migrator. Do not change the arguments, exit code, or output of a command the change does not name. Before you report done, run every command in the original requirements once (or the prior test suite) against the changed program and compare with the pre-change behavior; a refusal that did not exist before is a regression you introduced.
   - Input validity is a business rule too. If the change text says a command's input must be non-empty, bounded, in a set, or related to a fact, write it as a `when` guard on that command, with a corpus case for the refusal. A check only in the domain API or host wrapper is bypassable through the command interface.
   - After editing, run `ik laws <machine.ik.toml>` and read `unguarded_arguments` (declared arguments no `when` reads), including those of any new command. It directs attention; it does not prove protection. Apply the same dispositions as BUILD step 8: a constraint on the value or on its relation to state (including one stated through a shared type such as an identifier grammar, encoded as `text_in($arg, 'A-Za-z0-9._-', 1, 64)`) needs authoritative enforcement proved by a direct runtime refusal; opaque data needs the statement that no additional constraint is required and no meaningless guard; an external assertion needs its trusted source named; a contract rule enforced only in host code is an unmet requirement to report, not a documentation item.
   - A length-bounded character-set grammar is a `when` guard, including on a new command: `text_in($arg, 'A-Za-z0-9._-', 1, 64)` for an identifier of 1 to 64 characters of A-Za-z0-9._-. An opaque label the contract does not constrain stays unguarded. Residual unmet requirements are only for grammars that are not length-bounded character sets. A host-only check of an expressible identifier grammar is still bypassable through the command interface.
5a. Existing-instance continuity is a test you run, not an assumption. Before you edit, copy the current project aside. Create a persisted instance with the copy, in a store you keep, and leave it mid-lifecycle (not terminal). After the change, run the changed program against that same store: `status`, then the next legitimate command for that instance. `corrupt_state`, `IK_MACHINE_MISMATCH`, or any refusal the old program did not give is a continuity break. A new `.ik.toml` version does not rewrite stored instances: keep the previous definition and route a persisted aggregate to it, and use the new definition only for newly created ones. The owner is `aggregate.owner` (TypeScript and Python) or `Owner()` (Go), read from a `show` through any loaded definition; open the retained definition whose `identity` equals it, never a "current default". State whether each changed rule applies to existing instances, as the change request says.
5b. A frozen definition cannot gain a command or a rule, and there is no migrator. If the change asks existing instances to accept a new command, rule, or field, you cannot meet it by editing the old definition, rewriting stored state, or adding a sidecar file, JSON overlay, or host status that decides what an old instance does: that makes the host a second authority, and a crash between the runtime commit and the file leaves them disagreeing. Instead leave existing instances on their original rules, refuse the new command on them with the code the change text names (or `invalid_state` when it names none), and list "not met for existing instances: no migrator" in the handoff with the number of instances you can observe. A validated snapshot-and-import migration is a separate step the task must authorize, with its own evidence. Never report success for the new behavior on an old instance that a sidecar backs.
6. `ik check <machine.ik.toml> --prior <old.toml> --profile <checks.toml> [--corpus <cases.json>] [--json]` evaluates the profile on the candidate and, where the referenced states and commands exist in both, on the prior. `regression` means a goal satisfied on the prior is not satisfied on the candidate. `not_comparable` is not unreachability. This does not upcast stored state and does not authorize a production commit. See `docs/ik-check.md` and `docs/change-evidence.md`.
7. `ik scenario run <machine.ik.toml> <scenario.json> --out <dir>` for the new behavior and for an unchanged obligation. Scratch only. Exit 0 is that file's expectations, not a proof about other inputs. `ik scenario reproduce <bundle-dir> --out <dir>` confirms a bundle. See `docs/scenarios.md`.
8. `ik evidence verify <evidence.json> --machine <machine.ik.toml> [--profile <checks.toml>] [--corpus <cases.json>] [--runtime-binary <path>] [--json]` recomputes identities. Exit 0 means every recorded axis that was recomputed matches. Exit 1 means stale or a different machine version. It does not migrate, rebind, or delete history. Omitting `--runtime-binary` leaves a recorded runtime digest `not_recorded` and does not by itself fail. A goal id with a different content digest is `stale_profile`. Old evidence does not satisfy a changed goal. See `docs/change-evidence.md`.
9. `ik regression promote <bundle-dir> --name <name> --reason <reason> [--into <dir>]` copies a reviewed bundle and writes `REGRESSION.json`. It does not rewrite expectations to make a failure pass. Exit 2 means a digest mismatch, a missing required file, or an existing destination. `ik regression run <dir>` re-executes promoted bundles in scratch. Exit 0 means every case reproduced. A runtime binary difference alone is not a failure. Re-running does not edit the promoted files. See `docs/workbench-report.md`.
10. `ik report <path> [--json] [--html <file>]` is the folded finding list for the handoff. It does not create a success fact. `ik handoff <behavior.json> --evidence <path>... [--kind delivery|change|recovery] [--json]` renders the handoff from that evidence. The first line is `Desmo change: <subject>`; `New in this version` is the declared prior-vs-new delta; `Why` quotes the `why {text, source}` you supply (the requirement behind the change; the handoff never writes it and refuses without it); new-instance witnesses are explored only; continuity, each new or changed rule to accept, and the version policy for existing instances (keep them on the old version until they finish, or drain and recreate on the new one) sit in the first block. Each new or changed guarded rule needs `rule_witnesses` (examples that tell the rule from its one-step variants); the human accepts a rule by `accepted_rules` entries carrying the guard hash and examples hash the handoff prints. These checks cover declarative machines only. Cited ids sit under `Exact evidence`. A two-column river map (changed state annotated, then `WHAT ELSE IS AT RISK`) sits in the first block; the command table follows. Mermaid is `ik diagram --format mermaid` only. Added commands are tagged `✚`. `continuity not demonstrated` when that evidence is absent. A claim is `exercised` only when its cited finding ids resolve to statuses that support that item's `claim` (`reconciled` may use `committed_exact` or `historical`; those statuses do not support `new_mutation` or `current_handle`). Uncited, missing, partial, or contradicted claims say so. See `docs/workbench-report.md`.
11. Optional specialist only when the question needs it: `ik analysis describe <manifest.json>`, then `ik analysis run <manifest.json> --request <request.json> --out <dir> [--timeout-seconds <seconds>]` in scratch, never against a production store. `ik graph export <machine.ik.toml> [--corpus <cases.json>] [--max-nodes <n>] [--max-depth <d>] --out <graph.json>` is model-level for that finite graph only. Neither blocks the native check or scenario. See `docs/analysis-adapters.md`.
12. Fill the change handoff in `skills/desmo/SKILL.md`. Cite profile diff, evidence verify, and scenario paths. List unrun claims. Old aggregates keep their `(machine_id, version, spec_hash)`. A rescue of a failed first build is rescue-and-change, not retroactive first-pass success.

Criterion origins: record where each decision point of each new or changed rule came from (`requirement`, `origins`, `acknowledged_origins` in the behavior file), as in `skills/desmo/build.md`. Quote only what the requirement names as `stated`; everything you chose is `chosen`.

What is missing: as in `skills/desmo/build.md`. A change handoff marks a definition gap `(new)` when the prior version did not have it, and expects the requirement to speak to new or changed commands only.

Lost reply during the exercise: build the request with `aggregate.prepare` (Go: `Prepare`) BEFORE sending, persist its JSON in the host's job record, `dispatch` it, and after a crash `reconcile` the restored copy (TypeScript `Machine.reconcile`, Python `Machine.reconcile`, Go `Machine.Reconcile`). Never derive a new id from a refreshed generation and never resend. `committed_exact` is history, not a current handle. `not_recorded` is not permission to retry. See `docs/client-recovery.md`.
